# 三个菜单 — 执行步骤（**两个版本，照着做即可**）

> 先判断你属于哪个版本，再往下走：
>
> | 版本 | 判断标准 | 起点 |
> |---|---|---|
> | **【一】未落库** | 库里**没有**这 44 张表（客户现场新库 / 全新 schema） | 版本一 · 步骤 1 |
> | **【二】已落库** | 库里**已有**这 44 张表（例如本地 `as_agent`） | 版本二 · 步骤 1 |
>
> 两个版本**从不落库的第 4 步 / 已落库的第 3 步之后完全一样** —— 统一走文末「公共步骤 A~F」。

# 【一】未落库 —— 全新建库

### 步骤 1｜建 schema
```sql
CREATE SCHEMA <目标schema>;
SET search_path = <目标schema>, public;   -- 后面所有脚本都靠它定位，务必先执行
```
> 交付的 DDL 里表名**全是裸名（不带 schema 前缀）**，所以换任意 schema 都能跑，**不锁库名**。

### 步骤 2｜宿主初始化（**必须先做**）
`agent` 模块**只读不建**宿主 RBAC 三张表（`sys_user` / `sys_role` / `sys_user_role`），缺了它鉴权会直接报表不存在。

| 顺序 | 文件（相对 `src/main/resources/sql/`） | 说明 |
|---|---|---|
| ① | `init_auth_gaussdb.sql` | RBAC 三张表（带 `IF NOT EXISTS`，可重复跑） |
| ② | `init_db_gaussdb.sql` | 平台与业务表（含列迁移补齐） |
| ③ | `init_db_comments.sql` | 表/列注释（可选） |
| ④ | `init_sample_data.sql` | 示例数据（**可选**，含 DELETE+INSERT，不需要就别跑） |

### 步骤 3｜建 `admin` 账号（🔴 仓库里**没有**这个 SQL，必须手工）
实测：`AuthInitializer` 的「建默认管理员」逻辑**写在 `app.init-sql-on-startup=true` 分支里**，
而该开关**默认 `false`** → **光跑步骤 2 的脚本，新库里没有能登录的账号**。
（`AuthController` 也只有 `/login`，没有注册接口。）

```sql
-- ① 角色：menu_permissions 必须是 ["*"]（裸星号 = 菜单全通），**不能是 '[]'**
--    2026-09-22 口径统一后，"谁是管理员"完全由这份数据决定：
--      · AuthService#getUserMenuPermissions 含 "*" ⇒ 登录返回 menus=["*"]
--      · 前端 menus.includes('*') ⇒ 路由全放行 + 侧边栏全渲染
--      · AuthInterceptor 另有 role_code=='admin' 兜底（防自锁），但菜单可见性只认数据
--    ⚠️ 写成 '[]' 的后果：admin 登录后**侧边栏全空**（menus 为空，非 '*' 分支遍历不到菜单）。
INSERT INTO sys_role (role_code, role_name, description, menu_permissions)
VALUES ('admin', '系统管理员', '拥有所有权限', '["*"]');

-- ② 用户：password 必须是 BCrypt 密文，不能明文
--    取值：在你**现有库**执行  select password from sys_user where username='admin';
--    把结果原样粘进来（这样密码与现有环境一致）
INSERT INTO sys_user (username, password, real_name, status)
VALUES ('admin', '<从现有库复制 password 字段>', '系统管理员', 1);

-- ③ 绑定
INSERT INTO sys_user_role (user_id, role_id)
SELECT u.id, r.id FROM sys_user u, sys_role r
 WHERE u.username = 'admin' AND r.role_code = 'admin';
```
> 备选：临时把 `app.init-sql-on-startup` 置 `true` 启动一次（自动建 `admin`/`admin123`），**建完立刻改回 false**。
> ⚠️ 它同时会跑 `init_db_gaussdb.sql` **和示例数据**，现场慎用。

### 步骤 4｜建表 —— 执行 `三菜单DDL/三个菜单_建表DDL.sql`
- **44 张表 / 730 条语句**；无外键（顺序无关）、无序列、**无 `IF NOT EXISTS`**（表已存在会直接报错，属预期）
- 3 条原 MySQL 风格 `MODIFY COLUMN` 加宽语句**已内联进列定义**，脚本里**已无 `ALTER`**

```sql
-- 跑完自检（期望 44）
SELECT count(*) FROM information_schema.tables
 WHERE table_schema = current_schema()
   AND table_name IN ( /* 用核对报告文档里的 44 张清单 */ );
```
→ **接着走「公共步骤 A」**。

### 步骤 2｜确认基础配置（**本平台基准，不要动**）
```sql
SELECT id, code FROM sys_data_source;                    -- 期望 ≥1，记下 id
SELECT lm_code, model FROM large_model_config;           -- 期望 lm_code == yml 里 agent.rule.parse-model-code
SELECT id, role_code FROM sys_role;                      -- 期望有 admin，记下它的 id（本地 = 1）
```

### 步骤 3｜🔴 加宽 3 列（**表若是旧脚本建的，必须做**）
**实测：不做这一步，数据一定导不进去。**
本地 `as_agent` 是早前用 `agent_模块建表_as_agent.sql` 建的，那份**不含加宽语句**：
- 导 `agent_rule` → `ERROR: value too long for type character varying(1000)`
- 导 `index_params` → `ERROR: value too long for type character varying(100)`

```sql
-- 用 PG 原生语法（3 条实测全 OK）；纯加宽、不丢数据
ALTER TABLE agent_rule   ALTER COLUMN rule_text         TYPE text;
ALTER TABLE agent_rule   ALTER COLUMN parsed_expression TYPE text;
ALTER TABLE index_params ALTER COLUMN columncomment     TYPE VARCHAR(1000);
```
```sql
-- 复核（期望：text / text / 1000）
SELECT table_name, column_name, data_type, character_maximum_length
  FROM information_schema.columns
 WHERE table_schema = current_schema()
   AND ((table_name='agent_rule' and column_name in ('rule_text','parsed_expression'))
     or (table_name='index_params' and column_name='columncomment'));
```
> 用交付 DDL 建的表（版本一）**已经是宽类型，跳过本步**。

→ **接着走「公共步骤 A」**。

# 🔴 实测踩坑清单（照做就不会重复踩）

| # | 坑 | 现象 / 规避 |
|---|---|---|
| 1 | **旧脚本建的表缺 3 列宽度** | 导入报 `value too long for type character varying(1000)/(100)` → 先执行版本二 · 步骤 3 |
| 2 | **openGauss 不支持 `INSERT ... ON CONFLICT DO NOTHING`** | 报 `syntax error at or near "CONFLICT DO"`（基线是 PG 9.2）→ 幂等改用「先 DELETE 本次导入的行，再全量重导」 |
| 3 | **`DbExec` 早期的切分 bug（已修）** | 旧版按「行尾分号」切分，遇到 `index_params.script` / `agent_rule.rule_text` 里**以 `;` 结尾的行**会把语句切碎 → 报 `Unterminated string literal`。**现已是状态机切分**，用最新编译的 `DbExec.class` |
| 4 | **按行提取 INSERT 会截断（已修）** | 多行文本字段让 INSERT 跨多行，`line.startswith("INSERT INTO ")` 只取到第一行 → 生成残缺 SQL。**提取也必须用状态机切分** |
| 5 | **PowerShell 传 `-Dxxx=yyy` 必须加引号** | 不加会被拆成 `-D` + `.encoding=UTF-8` → 报「找不到或无法加载主类 .encoding=UTF-8」。**所有 java 命令的 `-D` 参数都写 `'-Dfile.encoding=UTF-8'`** |
| 6 | **表已存在会直接报错** | DDL 里没有 `IF NOT EXISTS` → 已落库的库**别跑整份建表脚本** |
| 7 | **重复导入会主键冲突** | 需重跑时：先 `DELETE FROM <表> WHERE <主键> NOT IN (<要保留的>)`，再重导 |
| 8 | **本地 admin 密码不是 `admin123`** | 实测 `/api/auth/login` 返回 401。要冒烟需先确认本地 admin 的密码（或重设） |
