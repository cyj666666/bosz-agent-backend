## 四、⚠️ 类型差异（2026-09-15 晚更新：14 条 → **11 条**）

### 4.1 「加宽差异」3 条 —— **已内联消除，不再是差异**

| 列 | 原 CREATE TABLE 里写的 | 公司脚本用末尾 ALTER 加到 | 线上实际 | 交付版现状 |
|---|---|---|---|---|
| `agent_rule.rule_text` | `VARCHAR(1000)` | `TEXT` | `TEXT` | ✅ 列定义直接写 **`TEXT`** |
| `agent_rule.parsed_expression` | `VARCHAR(1000)` | `TEXT` | `TEXT` | ✅ 列定义直接写 **`TEXT`** |
| `index_params.columncomment` | `VARCHAR(100)` | `VARCHAR(1000)` | `VARCHAR(1000)` | ✅ 列定义直接写 **`VARCHAR(1000)`** |

**改法与理由（2026-09-15）**：公司脚本原写法是 **MySQL 风格 `ALTER TABLE ... MODIFY COLUMN`**，
放在文件末尾做「事后加宽」。交付版**已把这 3 条的最终类型直接内联进各自的列定义**，
原语句以注释形式保留在原位（可追溯）。

- **为什么改**：`MODIFY COLUMN` 属 MySQL 兼容语法，**纯 PG 模式的库上可能不被支持**；
  内联后脚本自洽，两种模式都能一次跑通，也不会出现"建表成功但字段没加宽"的**静默偏差**。
- **改对了吗**：改完重跑类型核对，差异由 **14 条降到 11 条**，这 3 条消失 →
  说明内联后的类型与公司库**逐列一致** ✅
- **旁证**：公司库 `index_params_version.columncomment` 仍是 `VARCHAR(100)`（未被加宽），
  与"脚本只 ALTER 了主表、没管版本表"完全对应 → 说明这 3 条 ALTER 在公司库上**确实执行过**。
- ⚠️ **本地 `as_agent` 这三列仍是窄的**（`rule_text`/`parsed_expression` = `VARCHAR(1000)`、
  `columncomment` = `VARCHAR(100)`）—— 因为本地是早前用 `agent_模块建表_as_agent.sql` 建的，
  那份脚本**不含加宽语句**。若要在本地自测长规则正文，需单独执行加宽（属写操作）。
