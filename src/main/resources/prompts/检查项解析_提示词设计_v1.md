# 「检查项解析」提示词设计 v1（草案）

> 用途：替代 amar-agent-server 里 `AgentSearchApiClient` 调用的外部千寻智能体「审查规则解析智能体」，
> 改由本项目自有 `LargeModelGatewayClient` + 本提示词完成「自然语言阈值 → 可执行 QL 表达式」的解析。
>
> 状态：**草案，待评审**。落地后建议放到 `src/main/resources/prompts/` 下由代码加载，不要硬编码在 Java 里。

---

## 一、原实现 vs 新实现的差异

| | 原实现 | 新实现 |
|---|---|---|
| 调用目标 | 千寻平台「审查规则解析智能体」（`agentSearch.url`，厂商账号，Token 2027-06-22 过期） | 本项目 `large_model_config`（走 `LargeModelGatewayClient`） |
| 报文协议 | 千寻 Agent 协议 `{session_no, agent_id, role_name, version, stream, no_interrupt, input}` | 标准 OpenAI `messages` |
| **指标名→编号映射** | **由智能体返回**（`指标确定` 字段），代码只做替换 | **由本项目查 `index_params` 本地完成**，不再信任模型 |
| 数据出域 | 规则文本发往厂商云 | 不出内网 |
| 提示词 | 在千寻平台上，代码里没有 | 本文件 |

**为什么改成本地映射更好**（不只是"更牛逼"，是更正确）：

1. **消除一类静默错误**——原实现如果智能体返回了一个 `index_params` 里不存在的编号，后端照样替换进表达式，
   直到执行阶段取不到值、表达式求值为 `null`，用户只看到"没命中"，根本不知道是指标没对上。
   本地映射可以在解析阶段就**明确报错**："阈值设定里的『XX 指标』在指标库中不存在"。
2. **指标库是唯一事实来源**——表达式最终要拿 `index_params` 的值来算，那它引用的指标**本来就必须**在库内。
   让外部模型决定这件事，等于让一个不了解本地库的角色做越权决策。
3. **可审计**——本地映射的每一步都能落日志/落库，出问题能查；模型返回的映射没法追溯。

**但要保留的能力**：模型仍然要负责「**这段自然语言该用哪几个指标、该怎么比较**」这个语义判断——
这是它真正擅长的，也是本地代码做不到的。所以分工是：

```
模型：自然语言 → 表达式（只写指标名）+ 哪些需要二次推理判断
本地：指标名 → 指标编号（查 index_params），未命中就报错
```

## 二、System Prompt

```
你是银行「智策引擎」系统的检查项解析专家。你的唯一任务：把业务人员用自然语言写的【阈值设定】
翻译成一条可被程序直接执行的判断表达式。

════════ 输出格式 ════════
只输出一个 JSON 对象，不要任何解释文字、不要 markdown 代码围栏、不要注释：

{
  "最终结果": "<表达式字符串>",
  "指标确定": { "<指标名称>": { "指标编号": "" } },
  "special_indicator_result": { "<指标名称>": "<提示词>" }
}

════════ 表达式语法（必须严格遵守，否则程序无法执行）════════
1. 指标占位写成 {指标名称}，花括号内【只写指标名称】，绝对不要写编号。
   正确：{应收账款前五大是否为关联方}=='是'
   错误：{2085641008898412545}=='是'、{应收账款前五大是否为关联方|2085641008898412545}=='是'
2. 比较运算符：==  !=  >  <  >=  <=
3. 逻辑连接词：and  or  not（小写；不要用 && || ！）
4. 集合判断用 in，如：{行业分类} in ('制造业','批发业')
5. 字符串值用【英文单引号】包裹；数字裸写，不加引号、不带千分位、不带单位。
   正确：{资产负债率}>70
   错误：{资产负债率}>'70%'、{资产负债率}>'70'
6. 整条表达式必须写在一行，禁止换行、禁止注释、禁止调用函数、禁止三目运算符(?:)。
7. 连接逻辑取值：
   - 出现"且 / 并且 / 同时 / 、"→ 用 and
   - 出现"或 / 或者"→ 用 or
   - 没有明确连接词 → 默认用 and
8. 一个比较式里只放一个指标。要比较两个指标的大小关系时，两个指标各自成项后用 and 连接。

════════ 指标选择规则（最重要，违反即失败）════════
- 只能使用【可用指标清单】中列出的指标名称，必须【逐字一致】：不能简写、不能补全、
  不能换同义词、不能改标点、不能加空格。
- 若业务概念在清单里找不到对应指标：
  · 绝对不要编造指标名称；
  · 把该概念写进 special_indicator_result；
  · "最终结果"里用你能找到的最接近的指标占位。

════════ special_indicator_result 使用场景 ════════
当某项判断【无法靠"取一个指标值再比较"得出】，必须经过理解、推理或跨项计算时，才放进来。
例如：判断是否构成关联方、判断交易背景是否合理、判断是否存在异常模式。

  键 = 指标名称（必须与"最终结果"里出现的占位完全一致）
  值 = 一段给大模型的提示词，【必须包含 &&$$data&&$$ 占位符】，执行时会被替换成该指标的真实值。
       提示词要明确要求只回答"是"或"否"。

  示例：
  "special_indicator_result": {
    "应收账款前五大是否为关联方":
      "请判断以下企业应收账款前五大客户是否构成关联方，只回答'是'或'否'，不要解释：&&$$data&&$$"
  }
如果所有判断都能靠指标值比较得出，special_indicator_result 输出空对象 {}。

════════ 输出前自检（逐条确认）════════
① "最终结果"里出现的每一个 {指标名称}，都必须在"指标确定"里有同名键，
   且该名称与【可用指标清单】逐字一致；
② 表达式里没有任何指标编号、没有任何中文标点、没有任何换行；
③ 输出是合法 JSON，可被 JSON.parse 直接解析。
```

## 四、后端适配要点

### 4.1 指标名 → 指标编号（本地映射，替代模型的 `指标确定`）

1. 用正则 `\{([^}|]+)\}` 从 `最终结果` 里抽出全部指标名称。
2. 逐个查 `index_params`：
   - 先按 `paramname` **精确匹配**（注意：GaussDB 里 `paramname` 是**全小写列名**，SQL 里别加引号）
   - 未命中再做**唯一模糊匹配**（`LIKE` 或去空格/全半角归一化后匹配）；**匹配到多条一律判失败**，不能猜
3. 命中 → 把 `{指标名称}` 替换成 `{指标编号|指标名称}`，产出 `parsedExpression`。
4. **未命中 → `parseCode = "error"`**，把未命中的名称清单原样返回给前端，让用户改。
   这是相比原实现最重要的改进：**在解析阶段就暴露问题，而不是执行阶段静默不命中**。

### 4.2 指标清单怎么喂（规模问题）

`index_params` 可能有很多行，全量塞进提示词有两个风险：token 超限、模型注意力被稀释。
建议**两段式**：

- **第一段（本地粗筛）**：用阈值设定的文本做关键词匹配 / 分词，从 `index_params` 里捞出一个
  候选短名单（比如 50～200 条）。粗筛要**松**，宁可多带不可漏带。
- **第二段（模型精选）**：把短名单作为 `indicatorCatalog` 喂给模型，让它在短名单内挑。

若指标库规模很小（几百条以内），可以直接全量喂，省掉粗筛。

### 4.3 调用参数

| 项 | 建议值 | 理由 |
|---|---|---|
| `temperature` | **0**（或 0.1） | 这是结构化抽取任务，要的是稳定复现，不是创造力 |
| `enable_thinking` | **false** | 原实现关掉了；且开思考会往正文混 `<think>` 块（`LargeModelGatewayClient.cleanContent` 能兜底，但没必要） |
| 输出解析 | 直接 `JSON.parseObject` | 提示词已要求裸 JSON；解析失败要**抛明确异常**并记原始返回，不要静默吞掉 |
| `lm_code` | 需**单独配一行** | 不要复用 `report.ai-analysis.lm-code`（那是报告模块的，改动会互相影响） |

### 4.4 `special_indicator_result` 的执行侧

- 存 `agent_rule_prompt`：`key = MD5(parsedExpression + specialIndicatorJson)`，与原实现一致。
- 执行时把 `&&$$data&&$$` 替换成真实指标值，**再调一次大模型**，`temperature=0`、`enable_thinking=false`。
- **注意**：原实现的 `&&$$data&&$$` 替换是**单个指标值**（`indexValueMap.get(key)`）。
  如果提示词里出现多个占位符，原代码只会替换第一个——**这是个已知缺陷**，建议改成全局替换。

### 4.5 与原代码的兼容

`AgentRuleServiceImpl.parseRule` 里这两段消费逻辑可以**基本不动**：
- `vo.setParsedExpression(...)`
- `MD5Util.MD5Encode(parsedExpression + specialIndicator, "utf-8")` + `baseMapper.replacePrompt(...)`

需要改的是「替换来源」：把原来读模型的 `指标确定`，改成读本地映射结果。

## 五、待确认 / 风险

1. **原智能体的提示词拿不到**。本提示词是**基于代码行为反推**的（从 `parseRule` 的解析逻辑、
   `QLExpressUtil` 的语法约束、以及那个 `main` 方法里的真实样例表达式
   `{2085641008898412545|应收账款前五大是否为关联方}=='是'` 推断）。
   建议仍向公司索取原提示词做对照——**格式契约能保证一致，但模型在"选哪个指标"上的判断习惯可能有差异**。
2. **解析质量需要回归验证**：建议准备一批（20～50 条）真实阈值设定文本，
   在新旧两套上跑一遍，**比对产出的表达式是否等价**，再决定是否切换。
3. **指标清单粗筛的召回率**是这套方案的单点风险：粗筛漏掉的指标，模型就永远选不到。
   上线前要用真实规则集验证召回率。
