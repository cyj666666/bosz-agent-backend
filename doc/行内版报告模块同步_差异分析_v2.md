### 1.2 时间线证据（方向：行内 → 外网，单向向前移植）

1. 行内两个仓库都是**单提交快照、无共同 git 历史**（commit 时间 2026-09-16 18:17）→ **无法 `git diff`，只能快照比对**。

3. 行内报告接口/模型 **包含外网 9/12~9/13 的全部设计**（`/instance/generate`、`/instance/process`、`/instance/create`、`/instance/renew`、`AI 分析`、`预警建议`、`block-content`、`ReportDetailVO`、`ReportGenerateResult`、`DefaultReportContentProvider`），差异全部是**增改**。

5. **外网报告代码自 9/13 之后一次都没被碰过**（9/14~9/17 的 15 个提交全在 `agent` 模块 + SQL）。
   ✅ 好消息：**外网的报告代码是干净的**，"用行内版替换外网报告本体"不会踩掉任何未提交成果。

### 2.3 语义级差异（后端）

#### （1）`ReportController` —— 行内多 3 个接口

```diff
+ @PostMapping("/submit")   Result<ReportNoResult> submit(@Valid @RequestBody ReportSubmitRequest req)
+ @GetMapping("/latest")    Result<ReportNoResult> latest(@RequestParam String checkTaskNo)
+ @GetMapping("/share-url") Result<Map<String,String>> shareUrl(@RequestParam(required=false) String pageParams, ...)
  private final CreditShareUrlService creditShareUrlService;   // ← 行内注入
```
`/submit` 与 `/latest` 是 **信贷（SSF）渠道专用**：只入一条 `status=111` 的记录，把状态机交给生成池，并对信贷侧把 `111` 映射成 `000`。

#### （2）`ReportService` / `ReportServiceImpl` —— 两套状态机

| 维度 | 行内版 | 外网版（现） |
|---|---|---|
| 状态流转 | `111-待处理 → 000-进行中 → 888-已结束`（**888 唯一终态**）；999 仅存量/极端基础设施保留 | `000-进行中 → 888-已完成 / 999-失败` |
| 发起入口 | `submit()`（信贷/SSF）+ `renew()` + `createReport()`，**统一收敛到同一内核心** | 只有 `renew()` + `createReport()` |
| 详情查询 | `latestC(checkTaskNo)` | `latest(checkTaskNo)` ← **只是改名** |
| 报告编号 | **流水号服务取号** `SeqGeneratorService`（`yyyyMMdd+8位序号`），支持前端传 `reportNo` 跳过取号 | `generateReportNo()` = `RPT+yyyyMMddHHmmss+4位随机` |
| 并发互斥 | `DistributedLockService`（`REPORT_INIT_*` 30s / `REPORT_VERSION_*` 10s 两把锁）+ `claimReport()` CAS 认领 `111/999 → 000` | **上游统一加分布式锁**；本服务只靠 `reportNo` 唯一约束 |
| 重跑清理 | `clearInstances(reportNo)` 重跑前清旧实例（避免撞唯一键） | **不做清理**，靠实例表唯一键拦截 |
| 数据采集 | 注入 `ReportDataCollectOrchestrator`，`generate()` 前先跑采集编排 | 无（外网无采集链路） |
| 失败兜底 | `buildBlockFailureNote()` 汇总块级失败 → 写 `fail_reason` **软备注**；`briefError(Throwable)` 摘要异常 | `markStatus(999)` + `markFailReason()` **硬失败** |
| 版本号 | `markDone()` 在锁内写入 `version` | `nextVersionOf(checkTaskNo)` |
| 生成线程池 | `reportGenerateExecutor`（`ReportGeneratePoolConfig`，`000` 超时兜底重置 `111`） | 无 |

# 10. 🔴 定案后的联调一致性检查（2026-09-17 用户拍板：**前端 = Vue3 版，后端 = `bosz-agent-backend`**）

> 口径确定：**外网以 Vue3 版前端为准**（后续要给行内客户），**后端用 `bosz-agent-backend` 作为适配后端**。
> 因此必须检查：**"行内口径的 Vue3 前端" ↔ "9/13 口径的外网后端" 能不能对上。**
> **结论：对不上，有 3 处会当场暴露的断链 + 2 处语义偏差。**

## 10.1 外网后端生成链路的实际形态（源码实证）

```
createReport()  → 只插一条 status=111（待开始），❌ 不触发任何生成
renew()         → 直接插一条 status=000（进行中）+ CompletableFuture.runAsync(() -> generate(no))  ✅ 能跑通
generate(no)    → 置 000 → process() → 成功置 888 / 失败置 999 + failReason
```
- 全工程 `@Scheduled` **只有** agent 模块的 `CallLlmUtil` 两处，**没有任何定时任务调 `ReportService.generate()`**。
- `ReportGenerateJob`（行内的**报告生成池**：捞 111 → CAS 认领 000 → 提交线程池）**外网不存在**。
- ⇒ **外网后端唯一能加工 111 的入口 = `POST /api/report/instance/generate`**，而这正是外网 React 版列表页那颗「生成」按钮调用的接口。

## 10.2 🔴 断链清单（按严重度）

| # | 症状 | 根因 | 证据 |
|---|---|---|---|
| **1** | **「发起报告」后永远停在「待开始」，报告再也出不来** | Vue3 前端按行内口径**删掉了列表页「生成」按钮**（`instanceGenerate` 成了**死导出**，全 `src` 无调用点）；而后端**没有生成池/定时任务**接手 111 | `api/report.ts:294` 定义 `instanceGenerate`，`ReportList.vue` 只调 `instanceCreateReport`；后端 `@Scheduled` 零命中 |
| **2** | **详情页「生成软备注」黄色横幅永远不出现** | Vue3 读 `detail.failReason`，但外网 `ReportDetailVO` **没有这个字段** → 恒 `undefined` | `useReportInstance.ts:375` `detailFailReason.value = data.failReason \|\| null`；`ReportDetailVO.java` 无 `failReason` |
| **3** | **「发起报告」弹框里的「报告编号（选填）」填了没用** | Vue3 弹窗有这个控件且会提交（`...(createForm.reportNo?.trim() ? {reportNo} : {})`），但外网 `ReportCreateRequest` **没有 `reportNo` 字段** → Jackson 静默忽略 | `ReportList.vue:218-222 / :400`；`ReportCreateRequest.java` 只到 `reportType` |
| **4** | ⚠️ 失败语义不一致 | 外网失败置 **`status=999`**；Vue3 按行内契约期望 **`status` 仍 888 + `fail_reason` 软备注** | `ReportServiceImpl:135/152` `markStatus(REPORT_STATUS_FAILED)` |
| **5** | ⚠️ `versions()` 查询**不含 111**，而前端 `runningVersion = 000 \|\| 111` | 外网 `versions()` 的 where = `000 \|\| (888 && version not null) \|\| 999` | `ReportServiceImpl:495-497`；`useReportInstance.ts:345-347` |

> **第 4 条的连带后果**：失败版本在列表页会多一条「失败」Tag（Vue3 有 999 渲染分支，不会崩），
> 版本下拉里 999 也能选中，但**点进去拿不到失败原因**（因为 `ReportDetailVO` 缺 `failReason`）。
> **「更新报告」这条路是通的**（外网 `renew()` 直接建 000 + 异步 generate，不经过 111）。

## 10.3 闭链方案（三选一，待裁决）

| 方案 | 做法 | 改动量 | 与行内的一致性 |
|---|---|---|---|
| **① 搬行内生成池**（最贴行内） | 搬 `ReportGenerateJob` + `ReportGeneratePoolConfig/Properties` + `DistributedLockService` + `RequestLock`相关 + `claimReport()` / `markDone()` / `clearInstances()` / `SeqGeneratorService` | **中**（~10 个类，且牵动 `ReportServiceImpl`） | ✅ 完全一致 |
| **② 后端自闭环**（最省） | `createReport()` 照 `renew()` 的写法，插 111 后 `CompletableFuture.runAsync(() -> generate(no))`；或把状态直接建 000 | **小**（1 个方法） | ⚠️ 失去「111 交给上游任务」的原设计语义，但**接口/前端零改动** |
| **③ 保留外网方案** | 前端恢复列表页「生成」按钮，由人工触发（`instanceGenerate` 复活） | 小（前端） | ❌ 与 9/16 已裁决的「列表页去掉生成按钮」冲突 |

另需一并决定：
- **2 号**：给外网 `ReportDetailVO` **加 `failReason` 字段**（+ `detail()` 里赋值）—— 否则前端软备注是死功能。
- **3 号**：给外网 `ReportCreateRequest` **加 `reportNo`**（选填，传了跳过取号）—— 或前端去掉那个控件。
- **4 号**：失败到底置 `999`（外网现态）还是 `888 + fail_reason`（行内/契约态）？若选后者，前端要保持"999 有渲染分支"以防存量数据。
