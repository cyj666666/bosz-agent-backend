## 1. 全局约定

### 1.1 路由

| 路径 | 页面 | 是否需登录 | 备注 |
|---|---|---|---|
| `/login` | 登录 | 否 | 独立布局 |
| `/` | → 重定向 `/reports` | 是 | |
| `/reports` | 报告列表 | 是 | |
| `/report/:id` | 报告详情 | 是 | **`:id` = 日检流水号 `checkTaskNo`**（不是 reportNo！） |
| `/credit/report` | 信贷跳转独立页 | **否（不套 AuthGuard / MainLayout）** | `?cipher=…[&demo=1]` |
| `/users` / `/roles` | 系统管理 | 是 | |
| `/agent/**` | agent 三菜单 | 是 | 本次新增 |

- **`basename`：`/plma`**（与行内一致）。`createBrowserRouter(..., { basename: '/plma' })`，并且 `main.tsx` 要做基路径兜底重定向：
  ```ts
  const BASE = '/plma';
  if (!window.location.pathname.startsWith(BASE)) {
    window.location.replace(BASE + window.location.pathname + window.location.search);
  } else { /* mount */ }
  ```
  ⚠️ 副作用：本地开发地址变为 `http://localhost:5173/plma/reports`（请知悉）。
- `vite.config.ts` 的 `server.proxy` 把 `/api` 代理到后端（行内是 `http://localhost:8080`），`base` 不设（默认 `/`）。

### 1.2 API 基址与鉴权

- `baseURL = '/api'`（**不是** `/api/agent`）。所以前端写 `/report/instance/page`，实际请求 `/api/report/instance/page`。
- 登录后 token 存 localStorage，后续请求带 `Authorization` 头。
- **免鉴权白名单**：`/api/credit/resolve`（信贷跳转解密接口，登录鉴权之外）。

### 1.3 业务响应码约定（🔴 易踩）

后端业务失败时 **HTTP 仍是 200**，靠响应体里的 `code` 区分。因此所有报告接口统一包一层：

```ts
async function expectOk<T>(p: Promise<ApiResponse<T>>): Promise<ApiResponse<T>> {
  const res = await p;
  if (res && res.code !== 200) throw new Error(res.message || '操作失败');
  return res;
}
```
→ Vue3 里等价实现一个 `expectOk`（或 axios 响应拦截器统一处理），**否则业务错误会被当成成功**。

### 1.4 格式约定

- 查询用日期：`yyyy-MM-dd`（`RangePicker` 取 `[0]=Begin`、`[1]=End`，**含当天**）
- 展示用时间：`new Date(t).toLocaleString('zh-CN')`，空值 → `-`
- 文本列空值兜底：`null | undefined | ''` → `-`（统一 `dash()` 函数）

## 4. 状态机与状态映射

### 4.1 报告状态

| 码 | 含义 | 说明 |
|---|---|---|
| `111` | 待开始 | 上游/发起后落表态 |
| `000` | 进行中 | 生成中 |
| `888` | 已完成 | **唯一正常终态** |
| `999` | 失败 | **仅存量/极端基础设施场景**，正常链路不再产生 |

### 4.2 各位置映射（🔴 这是"交互一致"的核心）

| 位置 | 111 | 000 | 888 | 999（**保留预留映射，不做隐藏**） |
|---|---|---|---|---|
| 列表页·状态列 | Tag `default`「待开始」 | Tag `processing`「进行中」 | Tag `success`「已完成」 | Tag `error`「失败」+ **有 `failReason` 时 Tooltip 显示** |
| 列表页·操作列 | 「进行中…」（灰字 `#999`） | 「进行中…」（灰字 `#999`） | 「查看」按钮 → `/report/{checkTaskNo}`（**用日检流水号做入口键**） | `-`（灰字 `#bbb`，无入口） |
| 详情页·版本下拉 | 标记「生成中」且 **disabled** | 标记「生成中」且 **disabled** | 正常可选 | **正常列出且可选**（不过滤） |
| 结果弹框 | — | — | 触发「最新报告已生成」 | **无失败弹框**（失败不通过弹框提示） |

> 🟢 **2026-09-16 二次核对修正（推翻上一轮的"统一隐藏"）**
> 行内口径：**`999` 已不再产生**（后端两处注释白纸黑字：`ReportServiceImpl` 第 49 行「999-失败仅在存量/极端基础设施场景保留，正常链路不再产生」；第 279 行「此处**不**置 999 —— 999 在正常链路不再产生，避免同一流水号出现『进行中』脏态」）。
> **但行内没有做任何"隐藏"动作**，999 的展示逻辑全部**保留**（防御存量）：
> - `ReportList` 的 `STATUS_MAP` 仍含 `999 → error/失败`，且有 `failReason` 的 Tooltip；
> - 列表**不做行过滤**（后端 `page(query)` 不默认排除 999）；
> - 版本下拉 **`displayVersions = versions`（不过滤）**，999 会出现**且可选**；
> - 后端 `claimReport()` 明确支持 **`111/999 → 000` CAS 认领**（存量失败可被重新加工），所以"可选"是有依据的，不是漏写。
>
> → **外网要"交互一致"，就要把旧版的 `filter(v => v.status !== '999')` 和 999 失败弹框一起去掉**，回归"照常展示 + 不做过滤"。
> → 上一轮我列出的「后端过滤 / 前端显隐」两个落点 **作废**，那是过度设计。

**版本下拉 label 规则**：`status==='000' || '111'` → `` `${V${version}}（${reportNo}）· 生成中` `` 且 `disabled`；否则有 `version` → `` `${V${version}}（${reportNo}）` ``；无 `version` → 只显示 `reportNo`。
**版本列表**：**不过滤**（含 999）；排序由后端给定（在途/无版本号在前，888 按版本从新到旧）。

### 4.3 失败提示（🔴 与旧外网版的关键差异）

- **不再有"生成失败"弹框**。
- 生成结束（888）时若 `failReason` 非空 → 详情页**正文顶部黄色横幅** `.report-fail-note`（`!` 图标 + 文案），**页面仍正常渲染正文**。
- 结果弹框**只有成功态**：「✓ 最新报告已生成 / 新版本报告已生成完成，点击「确认」后页面将自动刷新到最新版本。/ 确认」，点确认 → 重新拉版本列表并切到最新已完成版本。

### 4.4 AI 全文分析：`RUNNING` / `DONE` / `FAILED`
### 4.5 预警建议：`PENDING`（排队中）/ `RUNNING` / `DONE` / `FAILED`
### 4.6 处置状态（风险 & 预警共用）：`PENDING` 待处理 / `ADOPTED` 已采纳 / `INVALID` 无效

**外网版做法**：把"明细页前缀 → 所属菜单键"登记成映射，再判权限：
```ts
const DETAIL_PARENT: Record<string, string> = {
  '/report': '/reports',
  ...agentDetailParents,        // agent 的三菜单明细页各自登记
};
const ALWAYS_ALLOWED = ['/'];
function resolveMenuKey(path) { const first = '/' + (path.split('/')[1] || ''); return DETAIL_PARENT[first] ?? first; }
```
**行内版现状**：只做前缀匹配 `menus.some(m => path === m || path.startsWith(m + '/'))`，豁免名单只有 `'/','/reports','/login'` → **`/report/{checkTaskNo}` 不在豁免里，非 admin 用户会被弹回列表**（除非菜单权限里额外登记了 `/report`）。

**结论：有必要整合进行内**，理由三条：
1. 修掉上面这个真 bug；
2. 整合 agent 三菜单后，agent 的「列表→详情」页**也**需要同一机制（`agentDetailParents`），否则一样会被弹回；
3. 成本极低（一个映射表 + 一个解析函数），且不影响现有权限逻辑。
