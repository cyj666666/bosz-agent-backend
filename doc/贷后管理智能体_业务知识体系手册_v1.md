## 第 0 章 怎么用这份手册

**三层读法**：

| 场景 | 读哪些章 | 目标 |
|---|---|---|
| 30 分钟速通 | 第 1、2、7 章 | 能讲清"这个系统是干什么的、钱从哪来到哪去" |
| 半天系统学 | 全部通读 | 能在白板上画出三层数据架构 |
| 考核前突击 | 第 9 章 + 附录题库 | 口径、红线、易错点，回答"为什么这么设计" |

**一条主线（记住这条，业务就串起来了）**：

```
   行内系统（信贷/征信/外数）
        │  ① 接口取数，落「源表层」
        ▼
   源表层 xd_* / zx_* / ws_* / dfs_*
        │  ② ETL 加工（清洗/对齐口径/转置/拼接），落「加工层」
        ▼
   加工层 app_*（45 张业务表）
        │  ③ 报告引擎按模板逐块取数
        ▼
   报告层 app_report_*（模板 + 实例 + AI 风险）
        │  ④ 前端渲染成一份可读、可编辑、可溯源的贷后检查报告
        ▼
   客户经理/审批人使用；AI 全文分析 → 预警建议 → 回流预警系统
```

**四句话概括系统价值**：
1. **省人力**：一份对公贷后检查报告原来靠客户经理手工翻十几套系统，现在自动取数 + 大模型成文。
2. **口径统一**：工商口径 vs 系统口径分表存储、分别取数，让"工商受益人≠系统实控人"这类差异**显性化**。
3. **可溯源**：每个结论都能点开看原始数据（表格溯源 / 链接溯源）。
4. **可留痕**：AI 给的是"建议"，人可采纳/无效，全过程留痕。

## 第 1 章 业务全景

### 1.1 贷后管理在整个信贷流程里的位置

银行对公信贷全生命周期：

| 阶段 | 业务动作 | 关键产物 | 本系统涉及 |
|---|---|---|---|
| 贷前 | 客户准入、评级、授信审批 | 授信批复 / 批复条件 | 读（批复要求） |
| 贷中 | 签约、放款、担保落实 | 借据、押品登记 | 读（借据/押品） |
| **贷后** | **放款后到结清前的持续监控与检查** | **定期检查报告、预警信号** | ✅ **本系统主战场** |
| 处置 | 逾期催收、不良化解 | 清收记录 | 读（逾期/五级分类） |

**贷后管理（Post-loan Management）**是监管硬要求：银行必须对已放款客户持续跟踪资金用途、经营变化、担保有效性、还款能力，并按频率形成**书面检查记录**。

### 1.2 「对公客户日常定期检查报告」是什么

- **对象**：对公客户（企业），不是个人。全库所有业务表都以 `customerId`（信贷客户编号）+ `customerName`（客户名称）为主键维度。
- **频率**：定期（按季/半年/年，由上游 `checkTaskNo` 检查任务决定）。
- **内容**：12 个章节 + AI 全文分析，覆盖客户工商、财务、征信、担保、押品、结算、预警、舆情等。
- **报告编号 `reportNo`**：贯穿**每一张**业务表的公共字段 —— 这是本系统最重要的数据组织键。

> 🔴 **考核点**：`reportNo`（报告维度）+ `customerId`（企业维度）+ `inputtime`（入库时间）三个字段**贯穿全部表**。
> 为什么按 `reportNo` 而不是 customerId 组织？因为**同一客户每期报告的数据要留快照**，规则引擎比对"授信时 vs 最新"才有依据。

### 1.3 为什么用 AI / 大模型

传统模式：客户经理手工查 10+ 套系统 → 复制粘贴 → 写分析 → 极易漏项、口径不一。

本系统：**模板驱动 + 规则引擎 + 大模型成文**：

| 环节 | 靠什么 | 说明 |
|---|---|---|
| 取哪些数 | **指标体系**（`index_params`） | 每个指标 = 一段 SQL + 数据源 + 参数 |
| 怎么判断风险 | **智策引擎**（`agent_rule`） | 规则表达式 + 阈值，命中才出风险 |
| 怎么成文 | **知识配置**（`knowledge_base_params`）+ 大模型 | 提示词模板 + 取数结果 → 大模型出文案 |
| 报告长什么样 | **报告模板**（`app_report_catalog` / `app_report_content_block`） | 章节树 + 内容块 |

## 第 2 章 信贷业务概念词典（贴代码版）

> 每个概念都给：**业务定义 → 本系统的表/字段**。这一章是"能跟业务人员对话"的基础。

### 2.1 主体类

| 概念 | 业务定义 | 本系统落点 |
|---|---|---|
| **对公客户 / 借款人** | 向银行借款的企业法人 | `app_customer_info`（系统口径）、`app_ic_info`（工商口径）、`xd_corp_customer_info`（源表 139 列） |
| **实际控制人** | 实际支配企业行为的自然人/法人 | `app_customer_info.actualController`（系统口径）、`app_ic_info` 的受益所有人字段（工商口径） |
| **股东 / 出资人** | 持有企业股权的投资方 | `app_shareholder_info`（工商·最新）、`app_ic_shareholder_info`（工商·变更）、`app_xd_shareholder_info`（信贷系统口径）、`ws_shareholder_info`（外数） |
| **担保人** | 为借款提供保证的主体 | `app_guarantor_info`（含 `subjectType` / `guarantorType`）、`app_guarantor_credit_info`（担保人征信） |
| **关联方** | 与借款人有控制/重大影响关系的企业 | 通过股东/实控人/对外投资关系推导；`app_customer_info` 带关联字段 |
| **集团/上级公司** | 借款人的母公司 | `xd_corp_customer_info.supercorpName`（上级公司名称） |

### 2.2 授信与放款类

| 概念 | 业务定义 | 本系统落点 |
|---|---|---|
| **授信（Credit Line）** | 银行批准给客户的**额度**（还没用） | `app_credit_use_info`（授信用信概况）、`xd_credit_info` |
| **用信 / 放款** | 客户在额度内**实际提款** | `app_credit_use_info`、`xd_credit_loan` |
| **借据（Loan Receipt）** | **每一笔**放款的凭证，一借据一记录 | `app_loan_receipt_info`（33 列，含放款日/到期日/余额/状态）、`xd_credit_loan` |
| **贷款余额 / 敞口** | 尚未归还的本金；敞口=余额-担保覆盖 | `app_loan_receipt_info` 的余额类字段 |
| **还款计划** | 分期的还本付息安排 | `app_loan_plan_info`（固贷/房开贷产品对象，客户级一行） |
| **担保方式** | 保证 / 抵押 / 质押 / 信用 | `app_guarantor_info`、`app_collateral_info` |
| **押品（Collateral）** | 抵押物/质押物 | `app_collateral_info`（主档）、`app_collateral_mortgage_info`（他项权利）、`app_collateral_restricted_right`（限制权利：查封/冻结） |
| **抵押顺位（rightOrder）** | 第几顺位受偿 | `app_collateral_info.rightOrder` —— 一押/二押风险差异巨大 |
| **受托支付** | 贷款资金**不经过借款人账户**，直接付给其交易对手（监管要求：防挪用） | `app_entrust_pay_info`（受托支付明细） |
| **贷款用途** | 资金约定用途（采购/工程/置换等） | `app_capital_flow_info`（资金用途及回流异常） |
| **结清 / 展期 / 逾期** | 正常还完 / 延期 / 未按期还 | `app_loan_receipt_info.loanStatus`（正常结清/提前结清/逾期结清/未结清） |

> 🔴 **考核点**：`loanStatus` 口径冲突时**以借据主档为准**（见 `ETL造数_合并_执行指南.md` §7.3）——
> 同一借据号在多处出现且状态矛盾时，`aflCreditLoanQry`（借据查询接口）是**唯一来源**。

### 2.3 风险分类类

| 概念 | 业务定义 | 本系统落点 |
|---|---|---|
| **五级分类** | **正常 / 关注 / 次级 / 可疑 / 损失**（后三类合称「不良」） | 征信表 `*_wjfl_*` 字段（五级分类余额）；`app_loan_receipt_info` |
| **不良贷款** | 次级 + 可疑 + 损失 | 同上 |
| **逾期（Overdue）** | 未按合同约定期限还款；按账龄分 M1/M2/M3… | 征信 `*_yqze`（逾期总额）、`app_loan_receipt_info` 逾期字段 |
| **关注类担保余额** | 对外担保被列为"关注"的金额 | `app_guarantor_credit_info`、征信 `qy_dwdb_bal_exc_wx`（对外担保余额-关注） |
| **预警（Early Warning）** | 风险信号触发，形成预警任务 | `app_early_warning_info`（台账）、`app_early_warning_signal_info`（信号）、`app_early_warning_opinion_info`（意见） |
| **舆情事件** | 负面新闻/司法/处罚 | `app_reputation_event_info`（借款人+股东双主体，授信后区间） |
| **企业图谱命中** | 关联关系图谱上命中风险点 | `app_graph_hit_info`、`xd_graph_hit` |
| **假冒国企** | 冒用国企名义的企业（监管重点） | 中台标签 `std_ecis_t_mining_tags_dd`；`app_shareholder_info.isFakeStateOwned` |

> 🔴 **五级分类记忆法**：`正常 → 关注 → 次级 → 可疑 → 损失`，**不良 = 后三类**。
> 从"关注"开始就要计提减值，这是贷后检查为什么盯"关注类"的原因。

### 2.4 财务与经营类

| 概念 | 业务定义 | 本系统落点 |
|---|---|---|
| **财报四件套** | 资产负债表 / 利润表 / 现金流量表 / 所有者权益变动表 | `app_finance_report_info`（主档：会计月/报表类型/口径/周期/是否审计/币种）、`xd_financial_report` + `xd_financial_subject` |
| **财务指标** | 由报表科目计算出的比率/金额 | `app_finance_index_info`（指标值，**一期一行一指标**）、`app_finance_indicator_info`（指标预定义，57 列宽表纵表） |
| **报表口径** | 合并/母公司/单户 | `app_finance_report_info` 的口径字段 |
| **同同比（YoY）** | 与上年同期比 | 指标表 `yoyValue` 字段（经验库"营收下降"规则直接读它） |
| **税务销售额** | 增值税申报销售额（与财报营收交叉验证） | `app_gs_tax_sales_info`（国税销售额，月粒度） |
| **国税财务数据** | 税务侧财务报表 | `app_gs_finance_data_info` |
| **代发工资** | 企业通过我行代发工资的规模（侧面反映经营真实度） | `app_payroll_stat_info`（近 12 个月，月粒度） |
| **结算账户/资产** | 在我行开立账户及日均存款 | `app_settle_account_info`、`app_settle_asset_info` |
| **结算交易对手** | 主要收付款对象（含前十大借贷方） | `app_settle_counterparty_info`（前十大）、`app_top_five_updown_info`（前五大上下游） |

> 🔴 **业务洞察（考核加分）**：`app_gs_tax_sales_info`（税务销售额）与 `app_finance_index_info`（财报营收）
> **同时存在**的目的就是**交叉验证** —— 税务数据难造假，财报数据易粉饰，两者差异大就是风险信号。
> 同理 `app_payroll_stat_info`（代发工资）用于验证"企业是否真在经营"。

### 2.5 征信类

| 概念 | 业务定义 | 本系统落点 |
|---|---|---|
| **企业征信报告** | 人民银行征信中心出具的**授信/负债/担保/逾期**全景 | `zx_ent_credit_info`（58 列）、`app_credit_report_info`（快照，52 列，**一期一行**） |
| **个人征信报告** | 自然人（实控人/股东/担保人）的负债与逾期 | `zx_per_credit_info`、`app_guarantor_credit_info` |
| **征信查询记录** | "谁查过我、查了几次"（频繁查询=资金饥渴信号） | `app_credit_query_info`（征信查询次数） |
| **征信债务明细** | 按债务类型拆的未结清余额 | `app_credit_debt_detail`（**按类型一期一行**，`debtType`） |
| **征信报告有效期** | 报告查询日到使用日的时限（通常 1 个月） | 经验库规则读 `app_credit_report_info.queryTime` 判断是否过期 |
| **国发征信** | 另一路征信数据源 | `gfzx_national_dev`、`gfzx_balance_sheet_item`、`gfzx_profit_sheet_item`、`app_guofa_report_info`（上游直给营收/应收/应付/存货，供财报偏差对比） |
| **对外担保** | 替别人担保的余额（或有负债） | 征信 `qy_dwdb_bal`、`qy_dwdb_bal_exc_wx`；规则"对外担保净资产比" |

> 🔴 **考核点**：征信数据是**一期一行**（`app_credit_report_info` 一期一行，`app_credit_debt_detail` 一期一类型一行）。
> 所以规则/文案取数必须按 `queryTime` 定位到目标那期，**不能"取最新一条就完事"**（不一定是最新那期才是业务要的）。

### 2.6 征信与财务的「交叉解读」（本项目最核心的业务设计之一）

**业务原理**：征信报告记录的是**金融机构报送给征信中心的负债**，财报记录的是**企业自己账上的负债**，两者天然存在差异：

| 对比维度 | 征信侧（银行视角） | 财报侧（企业视角） | 差异含义 |
|---|---|---|---|
| 短期借款 | `app_credit_report_info` 短期未结清 | `app_finance_index_info` 短期借款 | 企业账上没体现的隐性负债 |
| 中长期借款 | 同上 | 同上 | 同上 |
| 对外担保 | `qy_dwdb_bal` | 表外事项 | 或有无披露 |

**本系统的实现**：`app_credit_debt_detail`（征信债务明细表）就是"征信解读分析-征信及财务交叉"的数据载体。

**实测样例**（`doc/公司库app_表清单.md` §三）：

| 报告编号 | 客户名称 | 征信查询时间 | 会计月 | 财报短期借款 | 征信短期未结清 | 短期相差 | 债务偏离度 | 对外担保净资产比 |
|---|---|---|---|---|---|---|---|---|
| RPT-202603-001 | 苏州XX精密机械制造有限公司 | 2026-06-24 | 202603 | 2550.00 | 350.00 | -2200.00 | 63.27 | 4.76 |

> 这张表就是"业务知识 + SQL 加工"的完美样本：**指标 SQL 做 INNER JOIN**（`app_credit_report_info` ⋈ `app_finance_indicator_info`），
> 算出相差值与偏离度。面试/考核时拿这个例子讲，最有说服力。

### 2.7 双口径原则（🔴 本项目最容易被问的设计）

**同一个业务事实，行内有两套数据**：

| 口径 | 来源 | 为什么不同 |
|---|---|---|
| **工商口径** | 市场监管总局（经外数/启信宝等渠道） | 企业**自行申报**，变更后按申报时间生效 |
| **系统口径（信贷系统）** | 行内信贷系统人工录入 | 客户经理**手工维护**，可能滞后或错误 |

**两套数据必须分表存储、分别取数**，让差异显性化：

| 要素 | 工商口径 | 系统口径 |
|---|---|---|
| 企业基本信息 | `app_ic_info` | `app_customer_info` |
| 法定代表人 | `app_ic_info` | `app_customer_info` |
| 实际控制人/受益所有人 | `app_ic_info`（受益所有人） | `app_customer_info.actualController` |
| 股东（最新） | `app_shareholder_info` | `app_xd_shareholder_info` |
| 股东（变更） | `app_ic_shareholder_info` | — |
| 是否国资/假冒国企 | `app_shareholder_info` / `app_ic_info` | 中台标签 `std_ecis_*` |

**由此派生的一批经验库规则**（规则引擎拿两个值自己比）：

- 工商受益人 ≠ 系统实控人
- 工商法定代表人 ≠ 系统法定代表人
- 工商股东名称 ≠ 系统股东名称
- 是否假冒国企

> 🔴 **红线**：两口径**绝不共用同一字段**（设计说明书明写）。公用字段会导致"到底哪个口径"无法追溯，规则判定失去意义。

## 第 3 章 数据源三域（源表层）

- **位置**：`src/main/resources/sql/20260819/源表层/{信贷,征信,外数}/`
- **设计约定**（每个 DDL 文件头都写着）：
  1. 英文字段名 **100% 照抄接口材料**（驼峰/全大写/原拼写错误**都不修正**）
  2. 公共字段：`reportNo` / `customerId` / `customerName` / `inputtime`
  3. `[string]/[date]/[datetime]` → `VARCHAR`（存原串）；`[double]` → `DECIMAL(18,2)`
  4. 子表用 `mainId` 逐层指向上级表主键，**不建物理外键**
  5. 接口返回**直接追加插入，不做去重约束**（源表层是"流水"，不是"主数据"）

> 🔴 **考核点**：为什么源表层不做去重？因为它是**接口返回的流水存档**，重跑/多期数据都要留痕；
> 去重是加工层（app 表）的职责。删掉这条设计，重跑接口就会丢历史。

### 3.1 信贷域（`xd_*`，34 张）—— 行内信贷系统

| 接口来源文件 | 落表 | 业务内容 |

## 第 4 章 数据加工层（`app_*`，45 张）

### 4.1 为什么要有加工层

源表层是**接口原样落库**，不能直接给报告用，原因：

| 问题 | 加工层的解决 |
|---|---|
| 字段名是接口原文，不可读 | 转成业务语义列名（`revenueYoy`、`overdueTotal`） |
| 一个业务事实散在多张表 | 合并成"报告可直接取"的宽表 |
| 接口是"行"结构（一笔一行） | 转置成"指标"结构（一期一行一指标） |
| 工商/系统两套口径混在一起 | 分表对齐 |
| 时点不清（授信时/最新/上年） | 加期字段（`accountMonth`/`statMonth`/`taxPeriod`/`queryTime`） |

### 4.2 加工链路（ETL）

**位置**：`src/main/resources/sql/ETL造数_合并/`

| 顺序 | 文件 | 语句数 | 加工内容 |
|---|---|---|---|
| ① | `01_外数加工_合并.sql` | 32 | 外数 → 工商/股东类 app 表 |
| ② | `02_客户企业概况加工_合并.sql` | 113 | 信贷客户 → 客户/授信/借据/检查类 app 表 |
| ③ | `03_押品加工_合并.sql` | 29 | 押品 → 押品三表 |
| ④ | `04_贷后检查加工_合并.sql` | 62 | 结算/资金/预警/舆情类 |
| ⑤ | `05_财务指标加工_合并.sql` | 7 | 财报 → 财务指标 |

**实测基线**：243 条语句 100% 通过（`doc/ETL造数_合并_执行指南.md`），39 张源表 → 38 张有数据 → 产出 34 段 app 表。

> 🔴 **两个必知的口径**：
> 1. **顺序不可乱**：`04` 依赖 `01` 建的 `ws_gs_info` 借款人照面行、`02` 建的 `xd_credit_info`/`xd_credit_loan`。**重跑必须从 01 开始**。
> 2. **源表 owner 唯一**：`ws_gs_info` 由 01/02 造、04 只 UPDATE。多组共用同一 DELETE 范围会互相清场（踩过）。

### 4.4 三层表体系与公共列

```
L1 报告层     app_report_info                         一次报告一条
L2 公共基础表  app_customer_info / app_ic_info / ...    跨模块复用的元属性与实体
L3 模块明细表  app_finance_index_info / app_credit_debt_detail / ...
公共列贯穿：id · reportNo · customerId · customerName · inputtime
```

**核心设计原则（考核必问）**：

1. **按"业务实体"分表，不按"展现形式"分表** —— 规则、文案、表格只是数据的三种消费方式；同一字段只存一份。
2. **实体只存一张表** —— 押品正文/规则/表格全从 `app_collateral_info` 取，不重复存。
3. **经验库规则不单独建表** —— 规则判断所需数据全部来自 L2/L3，命中逻辑与结果存储交给**公司规则平台**。
4. **"一期一行"** —— 多期数据靠期字段区分（`accountMonth`/`statMonth`/`taxPeriod`/`queryTime`），规则按需 `WHERE 期 = 目标期`。

### 4.5 时间窗口（Excel N 列 17 种取值的处理）

| 取值 | 处理 |
|---|---|
| 最新 / 最新一期 | 单值字段存最新 |
| 授信时 / 上年 / 上上年 / 每月 | 走"一期一行"，用期字段区分 |
| 授信时 vs 最新对比 | 工商股东变更 `snapshot_type`；财务指标通过 `app_credit_use_info.creditDate` 反查报表期 |

> 🔴 **考核点**：`snapshot_type` 是"多时点快照"的实现方式 —— `app_ic_shareholder_info` 用它区分
> "授信时 / 最新"两个时点的股权结构，规则"授信后股权变更"就靠它比对。

### 5.1 分层

| | `app_report_content_block` | 内容块（**282 行 / 198 块**），描述"每块内容怎么取、怎么渲染" |
| **实例层** | `app_report_content_instance` | 本次报告每块的实际内容（**937 行**） |
| | `app_report_ai_risk` | `analysisType=RULE` 命中后 1:1 生成的风险明细（**75 行**） |
| | `app_report_ai_analysis` | AI 全文分析（可多次） |
| **预警建议** | `app_report_warning_advice` | 逐条建议（采纳/不采纳） |
| | `app_report_warning_advice_batch` | 批次（状态/模型/失败原因） |
| **留痕** | `app_report_risk_edit_log` | 风险要点修改记录 |
| | `app_report_action_log` | 用户行为流水（**只增不改**） |
| **提示词** | `app_report_prompt` | 提示词表（`promptCode` 取用） |

> 🔴 **业务概念**：**模板层 vs 实例层** —— 模板是"报告长什么样"（与具体报告无关，改了所有报告一起变）；
> 实例是"这次报告每块的实际内容"（快照，不受模板变化影响）。
> **目录不建实例表**：章节结构改了，历史报告的章节名会跟着变；内容块实例是快照的、不受影响。这是**已知且接受**的设计。

### 5.2 报告状态机（🔴 高频考核点）

```
   111 待开始 ──→ 000 进行中 ──→ 888 已完成（唯一终态）
  （上游预生成）   （加工中）        │
                                   └─ fail_reason 软备注：哪些块失败了
  
   999 失败 = 预留状态，正常链路不再产生（仅历史存量记录还在用）
```

| 状态 | 含义 | 谁置的 |
|---|---|---|
| `111` | 待开始（报告记录初始状态） | **上游**预生成 |
| `000` | 进行中（加工期间保持） | 定时任务取到待开始记录后 |
| `888` | **已完成（唯一终态）** | 加工结束（无论成功与否） |
| `999` | 失败 | ⛔ 已废弃，仅兼容历史数据 |

> 🔴 **最关键的一条口径（和旧认知不同！）**：
> **模板缺失 / 校验不通过 / 单块加工失败 / 落库失败，都【不再】中断链路、【不再】置 999**，
> 而是「空壳或跳过该块 + 原因汇总进 `fail_reason` 软备注」，报告**仍走 888 终态**。
> ⇒ **"报告完成但内容不全"看 `fail_reason`，不看 status。**
> 这是对齐行内口径的刻意设计：报告**必定达 888**，避免用户看到"失败"两个字就慌。

> ⚠️ **"静默失效"风险（必须知道的坑）**：
> **取数抛异常 = 没有值**（只记 ERROR 不外抛）⇒ 与"查到 0 行"**同形**。
> 报告 7 种结局里有 6 种正文长得一样 ⇒ 用户会把"没校验"读成"没风险"。
> 所以排查问题时，**必须翻日志和 `fail_reason`，不能只看页面**。

### 5.3 内容块的两个正交维度（🔴 设计精华）

| 维度 | 回答的问题 | 取值 |
|---|---|---|
| `fillType` | **怎么渲染** | `TITLE` / `TEXT` / `TABLE` / `SOURCE_LINK` |
| `analysisType` | **内容从哪来、怎么加工** | `ANALYSIS` / `RULE` / `TRACE_TABLE` / `TRACE_LINK` / `EXTERNAL` |

**行型矩阵（背下来，这块业务就通透了）**：

| 行型 | fillType | analysisType | 加工方式 | 空数据策略 |
|---|---|---|---|---|
| 报告头 | TITLE / TEXT | — | 固定文案（客户名 / "日常贷后检查报告"） | PLACEHOLDER / HIDE |
| 知识库（正文） | TEXT | `ANALYSIS` | 按知识库编号调大模型取文案 | PLACEHOLDER |
| **经验库（规则）** | TEXT | `RULE` | 规则判定 → **命中才取"补充分析"** | **HIDE** |
| 风险要点总结 | TEXT | `ANALYSIS` | 汇总全部命中的 RULE 块 → 1 次大模型归纳 | HIDE |
| 风险要点条目 | TEXT | `ANALYSIS` | 复用对应 RULE 块内容 + 跳转锚点 | HIDE |
| 表格溯源 | TABLE | `TRACE_TABLE` | 查业务表 → 拼 md 表格 | HIDE |
| 链接溯源 | TEXT | `TRACE_LINK` | 拼"链接开头" + SM4 加密跳转 | HIDE |
| 外部灌入 | TEXT | `EXTERNAL` | 别的接口直接落 content | PLACEHOLDER |

**空数据策略（`emptyStrategy`）**：

- `PLACEHOLDER`（**默认**）：显示"暂无数据"占位
- `HIDE`（需显式配置）：整块不渲染

> 🔴 **`HIDE` 的妙用**：经验库规则"命中的才出现"就是靠它 ——
> 模板里**静态配满 48 个**风险要点条目块 + `HIDE`，没命中的块内容为空 → 整块不渲染 → 视觉上只出现命中的那几条。
> **零前端改动**就实现了"动态列表"。

### 5.4 「AI 风险」= **命中的**经验规则（业务语义）

**一条经验规则命中 = 一条 AI 风险行**，同一行装两个产物：

| 列 | 内容 | 来源 | 可编辑 |
|---|---|---|---|
| `risk_desc` | **补充分析**（大模型出的风险文案） | 大模型 `answer` | ✅ 改正文时同步 |
| `check_result` | **校验结果**（是否命中，`VARCHAR(16)`：命中/未命中） | 规则引擎返回 | ❌ 只读留痕 |

**"命中"的判定依据 = 块内容非空**。一处判定、三处复用（正文 `HIDE`、风险行生成、风险要点总结素材），不会错位。

> 🔴 **"校验失败" ≠ "未命中"**：
> 表达式无法执行时 `resultStatus=null`，若混为一谈，就是把"这次校验根本没成立"伪装成业务结论。
> 后端单列一类日志便于排查。**这是业务严谨性的体现，考核时值得主动说。**

### 5.5 风险处置与预警

| 概念 | 取值 |
|---|---|
| 风险处置状态 | `PENDING` 待处理 / `ADOPTED` 已采纳 / `INVALID` 已无效 |
| 建议预警等级 | `RED` 红色 / `ORANGE` 橙色 / `YELLOW` 黄色 |
| 分析状态 | `RUNNING` / `DONE` / `FAILED` / `PENDING`（批次排队） |

**预警建议链（业务价值最高的闭环）**：
```
AI 全文分析（对整份报告做总结）→ 生成预警建议（逐条带等级）→ 人工采纳/无效
   → 采纳的建议 【回流预警系统】（pushWarningSignal）→ 形成正式预警台账
```
> 这一步把"报告"变成了"风控动作"，是业务闭环的关键。

### 5.6 溯源的两类设计

| 类别 | fillType | analysisType | content | 前端行为 |
|---|---|---|---|---|
| **表格溯源** | TABLE | `TRACE_TABLE` | 查业务表 → 拼 md 表格 | 点击弹大窗展示表格 |
| **链接溯源** | TEXT | `TRACE_LINK` | "链接开头" + SM4 加密 | 点击跳信贷系统 |

- 表格溯源的 `agentCode` 存**业务表英文名**（`app_customer_info`），带**白名单校验**（`^app_[a-z0-9_]+$`）防注入。
- 表头从 `pg_catalog` 取列中文注释，在第一个「（」处截断。
- **全列输出不过滤**（`id`、入库时间等技术列也保留）。
- 无数据/表不存在/异常 → **return null**（块空 → HIDE，不报错、不中断整份报告）。

> 🔴 **为什么溯源不用 `SOURCE_LINK`**：前端把 `SOURCE_LINK` 渲染成 `<a href="${content}">` 外链按钮，
> 而表格溯源 content 是 md 表格文本 → 会渲染成 `<a href="| 表名 |…">` **直接坏掉**。
> 所以"溯源"放进 `analysisType` 维度，`fillType` 只管渲染 —— **两个维度正交**。

## 第 7 章 报告生成全链路（端到端）

### 7.1 全流程

```
① 上游预生成报告记录（status=111 待开始，reportNo 唯一）
        │
② 触发：定时任务扫描 / 手动发起
   ├─ markStatus(reportNo, "000")   置进行中
   └─ reportGenerateExecutor 异步执行（core2/max4，一份报告一个任务）
        │
③ doProcess(reportNo)  —— 【两阶段】
   ├─ 载模板（loadEnabledCatalogs / loadEnabledBlocks，只取 isEnabled=1）
   ├─ validateTemplate()  模板校验（错则 fail-fast：空壳 + 软备注）
   │
   ├─ 阶段 1【并发】：逐块实例化（reportBlockExecutor，默认 5 路）
   │    普通块 → provider.provide() → 调智能体（知识库 getPromptContent / 规则 executeRule）
   │    TITLE   → blockName 兜底（不调 agent）
   │    跳过 RULE_SUMMARY 与 RULE_ENTRY#*（依赖阶段 1 结果）
   │    ⇒ 约 93 次大模型调用（45 知识库 + 48 规则）
   │
   ├─ 阶段 2【串行】：回填「风险要点」
   │    总结块 ← 汇总阶段 1 全部 RULE 块内容 → 1 次大模型归纳
   │    条目块 ← 复用对应 RULE 块 content（本地截取，不调模型）
   │
   └─ 落库：clearInstances + 逐行隔离插入（app_report_content_instance / app_report_ai_risk）
        │
④ markDone → status=888（唯一终态）；单块失败收进 blockFailures → fail_reason 软备注
        │
⑤ 前端详情页渲染（useReportInstance.ts）：目录树 → 块 HTML → AI 风险列表 → 溯源入口
        │
⑥ AI 全文分析 → 预警建议（批次）→ 人工采纳 → 回流预警系统
```

### 7.2 为什么必须两阶段（🔴 高频提问）

**总结块 `sortNo=20` 排在各章节 RULE 块（`sortNo` 30+）之前**。
按原顺序一阶段加工时，总结块要用的 RULE 内容**还不存在**。
⇒ 用 `ReportGenerateContext` 承载阶段 1 的 RULE 内容，阶段 2 从内存取，不查库。

### 7.3 为什么要两套线程池（🔴 高频提问）

| 池 | 并发单位 | 用途 |
|---|---|---|
| `reportGenerateExecutor` | **一份报告** | 发起/更新后异步触发加工（core2/max4） |
| `reportBlockExecutor` | **报告内一个内容块** | 块级并行调智能体（core = max = `report.agent.block-pool-size`，默认 5） |

**两层不能合并**：一份报告有 93 个取数块，若块级并发占用生成池，
**一份报告就把池吃满**、第二份只能排队；而且生成池的 `CallerRuns` 兜底会拖住发起报告的 Web 线程。

### 7.4 耗时与并发（业务视角）

93 次大模型调用，串行按单次 20~60s 算 = **30~90 分钟**，串行绝对不可接受。
采用**受控并发**（默认 5 路）。⚠️ 需确认大模型网关的并发上限。

### 7.5 报告详情页的两条入口（前端契约）

| 入口 | 路由 | 说明 |
|---|---|---|
| 报告列表 | `/report/:id` | `route.params.id` 取报告号 |
| 信贷系统 | `/credit/report?cipher=` | `CreditReport.vue` 解密后包一层，传 props |

**两条入口共用同一个 `ReportView.vue`** ⇒ 渲染改动**只改一处、两条入口天然同步**。
两者靠 **5 个 props** 区分语义：`checkTaskNo`、`hideBackButton`（信贷页 true）、`canRenew`（是否可重做）、`isRiskApply` / `workid`（缺省 = 不推信贷）。

### 7.6 用户可做的操作（业务功能清单）

| 操作 | 说明 |
|---|---|
| 查看报告 | 仅 **888 已完成** 状态可打开详情页 |
| 重做（`renew`） | 同一 `checkTaskNo` 生成新版本（`versions` 版本下拉） |
| 编辑风险要点 | 正文侧改正文会**同步** `risk_desc`；改动留痕 `app_report_risk_edit_log` |
| 风险处置 | 采纳 / 无效（`ADOPTED` / `INVALID`） |
| AI 全文分析 | 对整份报告做总结（可多次，`app_report_ai_analysis`） |
| 预警建议 | 逐条建议 + 采纳 → 回流预警系统 |
| 溯源 | 表格溯源弹窗 / 链接溯源跳信贷 |
| 导出 | Word 导出（`ReportWordExportService`） |

### 9.2 设计与代码类

| # | 红线 | 说明 |

| 10 | **唯一性只约束 `blockCode`，不约束 `agentCode`** | `agentCode` 跨章节按不同入参复用是**合法配置**（如"六、征信"借款人 vs "十二、担保人征信"担保人） |

| 12 | **TABLE 留作声明** | 前端 TEXT/TABLE 渲染一致，TABLE 不做渲染分支、也不做校验约束 |
| 13 | **`emptyStrategy` 默认 PLACEHOLDER** | DDL 默认值 / 代码 fallback / DML 数据三层统一 |
| 14 | **经验库规则不建表** | 只提供源数据，命中逻辑交公司规则平台 |
| 15 | **模板层 vs 实例层** | 目录改了历史报告章节名会变（已知、接受）；内容块实例是快照 |
| 16 | **999 已废弃** | 失败走 888 + `fail_reason`，新代码不再置 999 |
| 17 | **"校验失败" ≠ "未命中"** | `resultStatus=null` 是"没校验成"，不是业务结论 |

### 9.3 工程红线类（技术，但和业务强相关）

| # | 红线 | 说明 |
|---|---|---|
| 18 | **GaussDB/openGauss（非 MySQL）** | 行内 M 模式：不认 `varchar`/`INT` 类型名、`SIGNED`、`CAST(AS char)`；`\|\|` 是逻辑或（用 `concat`）；`to_char` **静默算错**；双引号=字符串常量 |
| 19 | **两库模式不同 ⇒ 只写交集语法** | 本地 `sql_compatibility=B`，行内 `M` |
| 20 | **动态数据源保持 `org.opengauss.Driver`** | 按 yaml 统一会导致 8+ 处判断落空 ⇒ 预览**静默返空** |
| 21 | **检索一律 `LOWER(x) LIKE LOWER(?)`** | |
| 22 | **动态取数禁用裸 `queryForList`** | 用 `DynamicDBUtil#queryForListCompat`（行内千分位会静默无值） |
| 23 | **`left()/substr()` 截中文报 UTF8 错** | 整列读出本地截；`length()` 返**字节数** |
| 24 | **"静默失效"是最大风险** | 取数抛异常 = 没有值，与"查到 0 行"同形 ⇒ 报告 7 种结局里 6 种正文相同 |
| 25 | **上游落表 `UpstreamEntityCopier` 会整段中断** | 任一字段类型不匹配即 `throw` ⇒ extra 与 insert 都不执行，接口仍 200、源头表无数据 |

> 🔴 第 24、25 条是**本项目最容易让业务方误判**的两条，
> 面试/考核时主动提，能直接体现"我不仅懂业务，还懂业务怎么被技术坑掉"。

## 附录 A 自测题库（含答案要点）

> 用法：先自己答，再对要点。**能答出 25 题以上，考核基本稳。**

**A 组 · 业务基础（1-8）**

1. 贷后管理在信贷全流程的哪个阶段？为什么必须有？
   → 贷中放款后到结清前；监管硬要求，持续跟踪资金用途/经营变化/担保有效性/还款能力。
2. 授信、用信、借据三者的关系？
   → 授信=批准额度；用信=实际提款；借据=每一笔放款的凭证（一借据一记录）。
3. 五级分类是哪五级？哪几类算不良？
   → 正常/关注/次级/可疑/损失；后三类为不良。
4. 什么是受托支付？为什么监管要求？
   → 贷款资金直接付给借款人交易对手、不经过借款人账户；防止资金挪用。
5. 为什么要比对"征信负债"与"财报负债"？举一个字段。
   → 征信=金融机构报送、财报=企业自报，差异即隐性负债；如短期借款 `短期未结清` vs 财报短期借款。
6. 抵押顺位（rightOrder）为什么重要？
   → 决定受偿顺序，二押及以上风险显著升高。
7. 什么是"假冒国企"？数据从哪来？
   → 冒用国企名义的企业；中台标签 `std_ecis_t_mining_tags_dd`，落 `app_shareholder_info.isFakeStateOwned`。
8. 代发工资数据（`app_payroll_stat_info`）在贷后检查里有什么用？
   → 验证企业是否真实经营（侧面证据），与税务/财报交叉验证。

**B 组 · 数据架构（9-16）**

9. 本系统的数据分几层？各层职责？
   → 源表层（接口原样落库）/ 加工层 app_*（清洗对齐）/ 报告层 app_report_*（模板+实例）。
10. 源表层为什么不做去重？
    → 它是接口返回的流水存档，重跑/多期要留痕；去重属加工层职责。
11. 贯穿全部业务表的三个公共字段？
    → `reportNo` / `customerId` / `inputtime`（+ `customerName`）。
12. 什么是双口径原则？举例说明为什么不能共用字段。
    → 工商口径 vs 系统口径；如受益人（工商）vs 实控人（系统）；共用则无法追溯来源、规则判定失去意义。
13. "一期一行"怎么实现？举两个期字段。
    → 表内带期字段；`accountMonth` / `queryTime`（还有 `statMonth`/`taxPeriod`）。
14. 源表加工的顺序为什么不能乱？举一个依赖。
    → `04` 依赖 `01` 的 `ws_gs_info` 借款人照面行、`02` 的 `xd_credit_info`/`xd_credit_loan`。
15. `snapshot_type` 干什么用的？
    → 多时点快照，区分"授信时/最新"（如工商股东变更）。
16. 征信表字段名为什么不改成人类可读？
    → 与人行报送口径逐字对齐，便于对账排查。

**C 组 · 报告体系（17-26）**

17. 报告有哪几个状态？唯一终态是哪个？
    → 111 待开始 / 000 进行中 / 888 已完成（唯一终态）/ 999 失败（已废弃，仅兼容历史）。
18. 单块加工失败会怎样？
    → 不中断链路、不置 999；跳过该块 + 原因进 `fail_reason` 软备注，报告仍走 888。
19. "报告完成但内容不全"该看什么？
    → 看 `fail_reason`，不看 status。
20. 模板层和实例层分别是什么？目录为什么不建实例表？
    → 模板=报告长什么样；实例=本次实际内容；目录是纯模板，改了所有报告一起变。
21. `fillType` 和 `analysisType` 分别回答什么问题？
    → fillType=怎么渲染；analysisType=内容从哪来怎么加工。
22. `emptyStrategy` 两个取值及默认值？
    → PLACEHOLDER（默认，"暂无数据"占位）/ HIDE（整块不渲染）。
23. "命中的规则才出现"是怎么实现的？
    → 模板静态配满条目块 + `emptyStrategy=HIDE`；未命中→内容空→整块不渲染，零前端改动。
24. 一条经验规则命中后落哪张表？装哪两样？
    → `app_report_ai_risk`；`risk_desc`（补充分析，可编辑）+ `check_result`（是否命中，只读）。
25. 为什么必须两阶段加工？
    → 总结块 `sortNo=20` 排在 RULE 块（30+）之前，一阶段时素材还不存在。
26. 溯源有哪两类？为什么不用 `SOURCE_LINK`？
    → 表格溯源 `TRACE_TABLE` / 链接溯源 `TRACE_LINK`；`SOURCE_LINK` 会渲染成外链按钮，md 表格装进去会坏掉。

**D 组 · 三菜单与生成（27-34）**

27. 一个"指标"在配置里由什么构成？
    → 一段 SQL（`script`）+ 数据源（`columnfromdatasource`）+ 参数 + 取值字段。
28. 指标树靠什么字段组织？核对时以哪个为准？
    → `parentparamno`；以 no 为准，`parentparamname` 常错。
29. 知识库调用哪三个参数有默认值陷阱？
    → `stream`（默认 true，必须 false）、`withModelSummary`（默认 false，必须 true）、`moduleCode`（必填）。
30. 走本地大模型时，模型输出取哪个字段？
    → `answer`（`content` 是 prompt 本身）。
31. 规则命中判定靠什么？补充分析素材哪 6 项？
    → QLExpress 执行表达式 `resultStatus`；处置意见/阈值设定/指标溯源/风险释义/命中结果/检查项名称。
32. 为什么要两套线程池？
    → 一份报告 93 块，块级并发占用生成池会吃满池、拖住 Web 线程。
33. 约多少次大模型调用？为什么这么大？
    → 约 93 次（45 知识库 + 48 规则）；模板按行建块，每个引用位置都要出现在正文。
34. 预警建议的业务价值闭环是什么？
    → AI 全文分析 → 建议 → 人工采纳 → 回流预警系统形成正式预警台账。

**E 组 · 设计与坑（35-40）**

35. 报告系统最大的风险是什么？
    → "静默失效"：取数抛异常=没有值，与查到 0 行同形，6/7 种结局正文相同 → 用户把"没校验"读成"没风险"。
36. `agentCode` 在报告内唯一吗？
    → 不唯一（跨章节按不同入参复用合法）；唯一性只在 `blockCode`。
37. 为什么源表落库会"接口 200 但没数据"？
    → `UpstreamEntityCopier` 逐字段拷贝，任一类型不匹配即 throw 中断，extra 与 insert 都不执行，只记日志。
38. 行内 M 模式有哪些坑？
    → 不认 `varchar`/`INT`、`SIGNED`；`||` 是逻辑或；`to_char` 静默错；双引号=字符串常量。
39. 详情页两条入口改渲染要改几处？
    → 一处（共用 `ReportView.vue`）；靠 5 个 props 区分语义。
40. `left()/substr()` 截中文会怎样？
    → 报 UTF8 错；应整列读出本地截；注意 `length()` 返字节数。
