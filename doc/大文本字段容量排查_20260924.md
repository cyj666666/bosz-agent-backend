# 大文本字段「容量风险」全库排查（2026-09-24）

> 扫描范围：`src/main/resources/sql` 下全部非备份 DDL（**132 个文件 / 去重后 4417 个列定义**）。
> 结论基于**仓库脚本口径**；实际结构用 §五 SQL 核对。

## 〇、大前提：行内 M 模式下 `TEXT` 只有 **64KB**

行内 = **集中式 GaussDB M 兼容模式**（内核 505.2.1.SPC0800，`sql_compatibility='M'`）。
该模式字符类型容量**与外网 openGauss(PG) 完全不同**（华为云 M-compat 开发指南）：

| 类型 | 行内 M 模式上限 | 外网 PG 模式 |
|---|---|---|
| `VARCHAR(n)` | 整列 **65,532 字节** | 无硬限（1GB 级）|
| `TEXT` | 🔴 **65,535 字节（64KB）** | **1GB** |
| `TINYTEXT` | 255 字节 | ⛔ 不认 |
| `MEDIUMTEXT` | ✅ **16,777,215 字节（16MB）** | ⛔ **不认** |
| `LONGTEXT` | ✅ 1GB-1 | ⛔ 不认 |

🔴 **所以"TEXT 能装 1GB"是错的** —— 它只有约 **2.1 万个中文**（65535/3）。
下表 §二 把所有 TEXT 列按"语义上会不会超 64KB"分了三级。

🔴 **关键修正：`prompt_query_result.query_result` 的 `Data too long for text` 不是"脚本与库不一致"** ——
它本来就是 `TEXT`，而 **M 模式的 TEXT 上限就是 65535 字节**。
"现有最大 32542"是**字符数**，中文按 UTF-8 占 3 字节 ⇒ 约 **9.7 万字节 > 65535** ⇒ 超了。
（**字符数看着没超、字节数早超**——本项目最容易误判的一类问题。）

## 五、核查 / 探针 SQL（✅ **探针已在行内跑过**，结论见下）

```sql
-- ① 确认实例形态与字符集
SHOW sql_compatibility;
SHOW server_encoding;

-- ② 实际列类型（核对脚本口径）
SELECT table_name, column_name, data_type, character_maximum_length
FROM information_schema.columns
WHERE table_name IN ('prompt_query_result','app_report_ai_analysis',
                        'app_report_warning_advice_batch','agent_rule')
ORDER BY table_name, ordinal_position;

-- ③ 探针：一次性验证 TEXT 上限、MEDIUMTEXT 可用性、VARCHAR(n) 的 n 语义
--    预期：TEXT 在 ~21845 个中文时报 Data too long for text；MEDIUMTEXT 可存 3 万+
CREATE TEMP TABLE t_probe (c_text TEXT, c_medium MEDIUMTEXT, c_varchar VARCHAR(2000));
INSERT INTO t_probe (c_text)   VALUES (repeat('中', 21845));  -- 65535 字节：应成功
INSERT INTO t_probe (c_text)   VALUES (repeat('中', 21846));  -- 65538 字节：应报 Data too long
INSERT INTO t_probe (c_medium) VALUES (repeat('中', 30000));  -- 90000 字节：应成功(若支持)
INSERT INTO t_probe (c_varchar) VALUES (repeat('中', 2000));  -- 2000 中文=6000 字节：
--    成功 ⇒ n 是「字符数」；失败 ⇒ n 是「字节数」
DROP TABLE t_probe;
```

### ✅ 实测结果（2026-09-24 已在行内执行）

| 断言 | 实测 | 结论 |
|---|---|---|
| `TEXT` 存 21845 个中文（65535 字节） | ✅ 成功 | — |
| `TEXT` 存 21846 个中文（65538 字节） | 🔴 **报 `Data too long`** | **TEXT 硬上限 = 65535 字节** |
| `MEDIUMTEXT` 存 30000 个中文（9 万字节） | ✅ 成功 | **MEDIUMTEXT 可用**（>64KB）|
| `VARCHAR(2000)` 存 2000 个中文 | ✅ 成功 | 🎉 **n 按字符数** ⇒ §三 风险解除 |

⚠️ 附带认知：报错而非静默截断 ⇒ 行内 `sql_mode` 含 `strict_trans_tables`，
**超长会直接报错中断业务**（不是悄悄截断）—— 所以这批 TEXT 列是**真·故障点**。

## 六、处置方向

🔴 **硬约束**：要突破 64KB 只能用 `MEDIUMTEXT` / `LONGTEXT`（MySQL 系专有类型），
而**外网 openGauss(PG) 不认** ⇒ **"一份脚本两库通吃"必然被打破**。二选一（或按字段分治）：

### 方案 ①：按环境分两份 DDL（保真）

- 行内把高风险 TEXT 列改 `MEDIUMTEXT`；外网保持 `TEXT`（PG 侧本来就是 1GB）。
- 落地形式：建表脚本拆成 `xxx_建表脚本.sql`（外网）+ `xxx_建表脚本_行内.sql`，
  或给一份行内专用的 `ALTER ... ALTER COLUMN ... TYPE MEDIUMTEXT` 脚本。
- ⚠️ **改存量表类型会重写表**（数据量大时耗时可观，需挑窗口）。
- 适合：报告正文 / 提示词 / 分析正文等**必须保真**的字段。

### 方案 ②：代码侧截断（两库一致，会丢内容）

- 入库前按**字节数**（⚠️ 不是字符数）判断并截断，超限打 WARN 留痕。
- 项目已有先例：`truncate(value, 1000)` 用于 `failReason`。
- 适合：快照 / 素材 / 中间结果 / 日志 —— **丢了不影响业务**。

### 方案 ③：大字段外移（库最瘦）

- 超长内容落文件 / 内容平台，库里只留引用（行内已有内容平台接缝）。
- 适合：快照 / 素材这类"排查时才看"的数据。改造成本最大。

📌 **建议按「能不能丢内容」分治**：

| 字段类型 | 建议 |
|---|---|
| 快照 / 请求体 / 查询结果（**能丢**） | **方案 ②** 按字节截断（或 ③ 外移）|
| 模型输出 / 正文（**不能丢**且确实会超的） | **方案 ①** 改 `MEDIUMTEXT` |
