## 一、这两张表是干什么用的

它们是**模板层**：描述"报告长什么样"，与具体报告实例无关。

```
app_report_catalog（目录树）          报告有哪些章节
        ↑ catalogCode
app_report_content_block（内容块）    每个章节里有哪些块、每块怎么取内容、怎么渲染
        │ (reportNo, blockCode) —— 实例层的行身份
        ↓ doProcess 逐块加工
app_report_content_instance（内容实例）  本次报告每块的实际内容
app_report_ai_risk（AI 风险明细）        analysisType=RULE 的块一对一生成的右侧风险列表
```

> 🔴 **目录不建实例表**（`detail()` 里写明）：目录是纯模板，改了所有报告一起变；只有内容块才落实例。
> 所以：**改章节结构 = 改 catalog；改某块内容 = 下次加工自然生效。**

### 1.1 `app_report_catalog` 字段

| 字段 | 设计含义 | 关键点 |
|---|---|---|
| `catalogCode` | 目录编号 | **全局唯一**（`uk_report_catalog_code`）；跨表关联键，`content_block.catalogCode` 指向它 |
| `catalogName` | 目录名 | 前端 `<h3>` 章节卡标题就是它（不是 TITLE 块！） |
| `catalogLevel` | 1/2/3 | 层级连续性（= 上级 +1）由**应用层**校验，DB 不管 |
| `parentCode` | 上级目录编号 | 一级为 NULL |
| `sortNo` | 同父下排序 | detail() 只按 `isEnabled=1` 取，停用即整节消失 |
| `isEnabled` | 1 可用 / 0 停用 | **旧模板就是靠这个下线的** |
| `inputtime` | 入库时间 | |

### 1.2 `app_report_content_block` 字段

| 字段 | 设计含义 | 关键点 |
|---|---|---|
| `blockCode` | 块编号 | **全局唯一**；同时是实例层行身份的一半，也是前端 DOM id（`anchorCode \|\| blockCode`） |
| `catalogCode` | 所属目录 | **NULL = 报告级块**（报告头），不进目录树、渲染在正文顶部 |
| `fillType` | `TITLE`/`TEXT`/`TABLE`/`SOURCE_LINK` | 决定前端怎么渲染 + 决定实例 content 的语义 |
| `analysisType` | `RULE`/`ANALYSIS` | **仅 TEXT/TABLE 有值**；RULE 会额外生成一条 AI 风险明细 |
| `agentCode` | 智能体编码 | **就是取数键**（本版 = 知识库编号 / 规则编号） |
| `blockName` | 块名 | RULE 时即**规则名称**（模板层与实例层同名同值） |
| `titleLevel` | 1/2/3 | 仅 TITLE |
| `emptyStrategy` | `PLACEHOLDER`（默认）/`HIDE` | 实例内容为空时：显示"暂无数据"占位 / 整块不渲染 |
| `jumpAnchorCode` | 跳转目标 | **单向**，值 = 目标块的 `anchorCode`（= 目标块 blockCode），前端滚动定位、不新开页 |
| `sortNo` | 同目录内排序 | 现有约定：溯源按钮固定 **900** |

### 1.3 从前端源码反推出来的三条硬约束（**必须遵守，否则静默失效**）

1. 🔴 **`titleLevel=1/2` 的 TITLE 块根本不渲染**（`useReportInstance.ts:165-168`：`titleLevel===3 ? <h4> : ''`）。
   章节标题由目录树的 `catalogName` 渲染成 `<h3>`。→ 所以 **B/C 列目录名要显示，只能用 `titleLevel=3` 的 TITLE 块**。
2. 🔴 **每个 catalog 都会渲染一张 `<section-card>`**（含空 html 的）→ **不能让任何目录挂 0 个块**，否则正文出现空白卡。
3. 🔴 **一个块只有 1 个 `jumpAnchorCode`**。demo 时代一个块里含多个跳转链接时必须拆块（`BLK_SUM_04/05/06` 就是这么来的）。
   → 这正是「（一）风险要点」要特殊设计的原因（见第四节）。

## 三、旧模板怎么下线 + 重导是幂等的

DML ② 段（旧模板下线）：

```sql
UPDATE app_report_catalog        SET isEnabled = 0 WHERE catalogCode NOT LIKE 'V2_%';
UPDATE app_report_content_block  SET isEnabled = 0 WHERE blockCode  NOT LIKE 'V2_%';
```

数据保留不删 → **回退只需把 V2 那批置 0**。`detail()` 的 `loadEnabledCatalogs()/loadEnabledBlocks()` 都过滤 `isEnabled=1`，所以停用后彻底不参与生成。

**DML ① 段（幂等清理，2026-09-17 新增）**：

```sql
DELETE FROM app_report_content_block WHERE substr(blockCode,   1, 3) = 'V2_';
DELETE FROM app_report_catalog       WHERE substr(catalogCode, 1, 3) = 'V2_';
```

改 Excel → 重跑生成器 → **直接重导本文件**即可，不用先手工清库（否则撞 `uk_report_catalog_code` / `uk_report_block_code`）。
三点说明：

- 用 `substr(code, 1, 3) = 'V2_'` 判前缀而**不是** `LIKE 'V2_%'` —— `_` 在 LIKE 里是单字符通配符，会误伤 `V2X%`。
- 删的是**模板行**，实例层（`app_report_content_instance` / `app_report_ai_risk`）存的是**快照 code**，
  且**无物理外键**指向模板表 ⇒ 重建模板**不影响历史报告**。
- 旧模板（非 `V2_` 前缀）**不删**，只置 `isEnabled=0`，所以两套可以共存、随时回退。

> ⚠️ 注意：`detail()` 里**目录树也来自模板层**，所以历史 888 报告的目录/章节名会跟着模板变（改 catalogName 会回溯影响老报告）。
> 内容块实例是快照的（不受影响）。**这是既有设计，本次未改**；如果要求"老报告目录不变"，需要另开方案（目录快照到实例层）。

## 四、🔴「（一）风险要点」的特殊设计

**需求**：基于**所有 `analysisType=RULE` 的内容块**做总结分析，**且支持跳转到下面具体的 RULE 块**。

**矛盾点**：一个块只有 1 个 `jumpAnchorCode`，而跳转目标是**多个**且**数量动态**（取决于本次命中几条规则）；
模板层块数是**静态**的，不能临时增删块。

**采用的方案：1 个总结块 + N 个"要点条目"块（N = 模板里 RULE 块总数，静态配好）**

| 块 | agentCode | 内容来源 | jumpAnchorCode | emptyStrategy |
|---|---|---|---|---|
| `V2_BLK_SUMMARY_A00`<br>`风险要点总结` | `RULE_SUMMARY` | provider 收集**本报告全部 RULE 块的已生成内容** → 拼素材 → 调大模型总结成一段 | 无 | PLACEHOLDER |
| `V2_BLK_SUMMARY_E01`…`E48`<br>= 各规则名 | `RULE_ENTRY#<对应RULE块blockCode>` | 复用对应 RULE 块的 content（本地截取要点，**不额外调模型**） | **= 对应 RULE 块 blockCode** | **HIDE** |

**为什么这样能成立**：
- 条目块**静态配满 48 个**，但 `emptyStrategy=HIDE` → **本次没命中的规则内容为空 → 整块不渲染** → 视觉上只出现命中的那几条，"动态"由显隐实现；
- 每个条目块只指向 1 个目标 → **完全用现有的块级 `jumpAnchorCode`，零前端改动**；
- 总结块排在条目之前（sortNo 20 vs 30…500），读者先看总结、再逐条点进去。

**顺带说明**：右侧「AI 风险识别」列表的每条风险本来就有 `jumpAnchorCode` 指向对应 RULE 块（`buildRisk()` 1:1 生成），
所以"跳到具体规则"这条能力**在风险列表里早就有了**，本设计是把它也做进正文。

## 五、真实内容怎么取（provider 接 agent）

> 落点：`ReportContentProvider.provide(ReportGenerateContext)`（`DefaultReportContentProvider` 是预留位）。
> `MockReportContentProvider` 现由 `report.mock-content.enabled=true` 启用 → 接真实链路时置 `false`。

### 5.1 ANALYSIS（知识库）—— 取「知识配置管理」该条详情页预览的大模型分析结果

```java
JSONObject p = new JSONObject();
p.put("moduleCode", block.getAgentCode());   // E 列的知识库编号
p.put("entName", customerName);              // 借款人（G 列的那类参数）
p.put("withModelSummary", true);             // 🔴 关键：true 才会真的调大模型出文案
p.put("stream", false);                      // 🔴 关键：默认是 true，不关流会走 SSE 分支拿不到文本
Object res = knowledgeBaseConfigService.getPromptContent(p.toJSONString(), null);
String content = ((JSONObject) res).getString("content");
```

链路：`getPromptContent` → `handlePromptContent()`（按 moduleCode 找知识库配置、渲染 prompt）
→ `invokeLlmIfNeeded()` → `withModelSummary=true` 时 `invokeLocalLlm()` → `callLlmUtil.callLlm(..., returnFlag=true, knowledgeQuery=true)`
→ `OpenAiChatUtil.doNonStream()` **同步返回** `{content: 全文}`。

**三个必须显式传的参数（都是默认值陷阱）**：
| 参数 | 默认 | 不传的后果 |
|---|---|---|
| `stream` | **true** | 走 SSE，`emitter=null` → 拿不到文本 |
| `withModelSummary` | false | 只返回渲染好的 prompt，**不调模型** |
| `moduleCode` | 空 | 直接返回 `{0}` |

另：知识库里若 `isCloudSearch=true` 会走 `invokeCloudLlm`（云端 RM1201），不经本地大模型 —— 需按实际配置确认。

### 5.2 RULE（智策引擎）—— 取该条详情页「补充分析」的大模型文案

直接复用 `AgentPromptController#getRule` 那段逻辑（**同一 JVM，不走 HTTP**）：

```java
AgentRuleEntity rule = agentRuleService.getRule(agentCode);
AgentRuleExecuteReq req = new AgentRuleExecuteReq();
req.setRuleCode(agentCode);  req.setId(rule.getId());  req.setRuleStatus(rule.getRuleStatus());
req.setParsedExpression(rule.getParsedExpression());  req.setPromptKey(rule.getPromptKey());
if (StringUtils.isNotBlank(rule.getFactAnalysis())) req.setFactAnalysis(rule.getFactAnalysis());
JSONObject params = new JSONObject();
params.put("entName", customerName);
params.put(SqlDataSetBuilder.STRICT_FETCH_KEY, true);   // 🔴 正式执行必须打：参数没传全时不许拿配置里的样例值兜底
req.setRequestParams(params);

AgentRuleExecuteVO vo = agentRuleService.executeRule(req);
if (!QLExpressUtil.getResultAsBool(vo.getResultStatus())) {
    return null;                       // 未命中 → 块内容空 → PLACEHOLDER/HIDE 生效
}
// 命中：把「补充分析」需要的素材拼进去（顺序与 getRule 一致）
JSONObject getParams = new JSONObject();
getParams.put("content", rule.getDisposalAdvice());      // 1 处置意见
getParams.put("input",   rule.getThresholdConfig());     // 2 阈值设定
getParams.put("data",    vo.getMatchedMetrics());        // 3 指标溯源
getParams.put("risk",    rule.getRiskRemark());          // 4 风险释义
getParams.put("result",  vo.getResultStatus());          // 5 命中结果
getParams.put("rule_name", rule.getRuleName());          // 6 检查项名称
if (StringUtils.isNotBlank(vo.getFactExpression())) getParams.put("factExpression", vo.getFactExpression());
getParams.put("moduleCode", "IntelligentStrategyEngine");
params.forEach(getParams::put);                          // 基础参数透传
getParams.put("stream", false);                          // 🔴 同上，必须关流
Object res = knowledgeBaseConfigService.getPromptContent(getParams.toJSONString(), null);
```

**语义与现有设计天然吻合**：`executeRule` 未命中 → 块内容为空 → **PLACEHOLDER 显示"暂无数据" / HIDE 整块隐藏**，
所以"没命中的规则不出现"这件事**不用额外写逻辑**。

### 5.3 两类特殊块的处理

| 块 | 处理 |
|---|---|
| `TITLE`（titleLevel=3） | **不调 agent**，content = `blockName`（`fallbackTitle()` 已有这套兜底，直接用） |
| `SOURCE_LINK` | 本质是按钮，content = 外链 URL；本次 Excel **没有溯源链接来源** → `emptyStrategy=HIDE`，取不到就不渲染 |
| `RULE_SUMMARY` | 见 §6.2，需要**两阶段** |
| `RULE_ENTRY#<blockCode>` | 从对应 RULE 块的 content 截要点，**不调模型** |

## 六、放进 `doProcess` 大流程

### 6.1 顺序问题（必须两阶段）

```
doProcess(reportNo)
 ├─ 载模板 / 校验（已有）
 ├─ 阶段 1：逐块实例化
 │    普通块 → provider.provide() → 调 agent    ← 93 次大模型调用（45 知识库 + 48 规则）
 │    TITLE  → blockName 兜底
 │    跳过 RULE_SUMMARY 与 RULE_ENTRY#*（它们依赖阶段 1 的结果）
 ├─ 阶段 2：回填「风险要点」
 │    总结块 ← 汇总阶段 1 全部 RULE 块的 content → 1 次大模型调用
 │    条目块 ← 复用对应 RULE 块的 content（本地，不调模型）
 └─ 落库（已有，clearInstances + insert）
```

> ⚠️ **不能一阶段搞定**：总结块 sortNo=20 排在各章节 RULE 块（sortNo 30+）**之前**，按原顺序加工时 RULE 内容还不存在。
> 用 `ReportGenerateContext` 里已有的上下文对象承载"阶段 1 的 RULE 内容"，阶段 2 直接从内存取，不查库。

### 6.2 耗时（🔴 这是最大风险，需你先定策略）

93 次大模型调用，**串行绝对不可接受**（按单次 20~60s 算 = 30~90 分钟）。可选：

| 方案 | 说明 | 代价 |
|---|---|---|
| **A. 受控并发**（推荐） | 专用并发池（如 6~8 路）跑阶段 1，池大小可配 | 要确认大模型网关的并发上限；失败块的软备注顺序会不确定 |
| B. 分章节并发 | 章节内串行、章节间并发 | 粒度粗、实现简单 |
| C. 先跑通不优化 | 只配几个块、串行验证链路 | 仅用于联调 |

另外 `report.generate` 线程池现在是 core2/max4 —— 并发跑 agent 需要**再开一个"块级并发池"**，不能占用生成池本身（否则一份报告就吃满）。

### 6.3 其他改造点

- `report.mock-content.enabled` 置 **false**（否则 Mock 优先，真实 provider 不生效）
- 每块的 `agentCode` 会被调 **93 次**；同一 agentCode 在不同章节出现多次（源表就有复用，如 `zxcxsjmsqy` 在「六」和「十二」各一次）→ 要不要**按 agentCode 去重**（同参数同结果，可缓存）？见 §7
- 软备注：单个块失败走现有的 `blockFailures` 机制（888 + 软备注），不需要新逻辑

### 8.3b 🔴 `validateTemplate` 的完整规则清单（2026-09-17 连撞两次后整理）

| 5 | `blockName` 非空 | 内容块缺少名称（blockName） |

#### 规则 4 的来龙去脉（2026-09-17 用户报错 `V2_BLK_SETTLEMENT_A01`）

**背景**：模板里有 5 个块 `fillType=TABLE`（源表「展现形式」列写了"表格"），其中
`V2_BLK_SETTLEMENT_A01` / `A05` / `A07` / `BUSINESS_A05` / `WARNING_A02`，**全部是知识库（ANALYSIS）**，无 RULE。

**原校验是**「analysisType 仅 TEXT 可配」，与本工程设计**自相矛盾**：

1. `AgentReportContentProvider#provide` 第 133-139 行明确把 TABLE 当可分析块：
   ```java
   boolean analysable = FILL_TEXT.equalsIgnoreCase(fillType) || FILL_TABLE.equalsIgnoreCase(fillType);
   if (!analysable || !StringUtils.hasText(block.getAnalysisType()) || !StringUtils.hasText(agentCode)) return null;
   ```
   ⇒ 它**要求** TABLE 块带 `analysisType`，否则直接 return null。
2. 原始 DDL 第 88 行注释本来就写着 `agentCode 仅 fillType=TEXT/TABLE 时有值`（第 51 行那条"仅 TEXT"是笔误）。
3. `ReportConstants.FILL_TABLE` 的注释：「表格（**content 为表格成品片段**）」—— 成品片段当然可以由 agent 产出。
4. 前端 `blockToHtml` 只对 `TITLE` / `SOURCE_LINK` 分支，**TABLE 与 TEXT 渲染完全一致**（都是 `${content}` 原始注入）
   ⇒ 保留 TABLE **不影响渲染**，只是保住了源表的「展现形式」语义。

⇒ **结论：放宽校验**（TABLE 也允许 `analysisType`），**不是**去清空那 5 个块的 analysisType ——
后者会让它们静默变空。同时把 `isRuleBlock` 从 `TEXT && RULE` 改为 **`(TEXT||TABLE) && RULE`**，
与 provider 的 `analysable` 统一口径，避免将来出现 `TABLE + RULE` 的块时「正文有内容、风险列表却少一条」。

> 💡 顺带一个待观察点：这 5 个 TABLE 块的 `content` 由大模型产出。若模型返回的是 **markdown 表格**，
> 而报告正文是 `${content}` 原始注入（不做 markdown 转换），页面上会看到 `| a | b |` 原文。
> 目前**未验证**（真实链路还没跑通），跑起来后重点看这 5 块。

### 8.4 块级并发池 + 两阶段 `doProcess`

**并发**（`report.agent.block-pool-size`，暂定 5）：

| 池 | 并发单位 | 用途 |
|---|---|---|
| `reportGenerateExecutor` | **一份报告** | 发起/更新报告后异步触发加工（core2/max4） |
| `reportBlockExecutor`（新增） | **报告内一个内容块** | 块级并行调智能体（core = max = blockPoolSize） |

🔴 **两层不能合并**：一份报告有 93 个取数块，若块级并发占用生成池，一份报告就把池吃满、第二份只能排队，
而且生成池的 `CallerRuns` 兜底会拖住发起报告的 Web 线程。

**两阶段**（`doProcess`）：

```
阶段 1（并发）：普通块（TITLE/TEXT/TABLE）→ provider.provide() → 调智能体
              「RULE_SUMMARY」与「RULE_ENTRY#*」这两类**跳过**（slots 留空）
阶段 2（串行）：总结块 ← 收齐阶段 1 全部 RULE 块内容 → provideRuleSummary() 调大模型归纳
              条目块 ← 直接复用对应 RULE 块的 content（本地，不调模型）
```

🔴 **为什么必须两阶段**：总结块 sortNo=20 排在各章节 RULE 块（30+）**之前**，一阶段按序加工时素材还不存在。

**「命中的才出现」怎么实现**：条目块模板里静态配满 48 个、`emptyStrategy=HIDE`；
某条规则未命中 → 对应 RULE 块内容为空 → 条目块内容也为空 → 整块不渲染。**零前端改动**。

**同一条规则在正文与风险列表的口径必须一致**（2026-09-17 补）：正文 RULE 块同样配 `emptyStrategy=HIDE`
（未命中不显示「暂无数据」），且后端**只对命中的规则**生成 AI 风险行 —— 两侧都按「块内容非空」判定命中，
不会出现「正文里没有、风险列表里却有」的错位。

**SPI 扩展**：`ReportContentProvider` 增加 default 方法
`provideRuleSummary(ReportGenerateContext, List<RuleHit>)`（默认返回 null，不支持的实现无需改动）。
真实实现放在 `AgentReportContentProvider`，用报告模块自己的
`LargeModelGatewayClient.chat(system, user)`（即 `report.ai-analysis.lm-code` 那套模型配置），
与「AI 全文分析 / 预警建议」同一套模型。

### 8.5 🔴 provider 调用踩到的三个坑（均已从源码确认）

| # | 坑 | 后果 / 绕法 |
|---|---|---|
| 1 | `getPromptContent` 的 `stream` **默认 true** | 走 SSE 分支、拿不到文本 → 必须显式 `stream=false` |
| 2 | `withModelSummary` **默认 false** | 只返回渲染好的 prompt、**不调模型** → 必须显式 `true` |
| 3 | `CallLlmUtil.finishEmitter()` **没有 null 判断**（直接 `emitter.complete()`） | 传 `null` 会在出错分支抛 NPE、**把真实错误原因整个吃掉** → 改传一个未初始化的 `SseEmitter`（Spring 在未绑定 handler 时 `send/complete` 只做缓冲不抛；且 `returnFlag=true` 时成功路径根本不碰它） |

**取值字段名也要注意**：走本地大模型时 `knowledgeQuery=true`，
`OpenAiChatUtil.doNonStream` 里写的是 **`answer` = 模型输出、`content` = prompt 本身** ——
拿 `content` 会把提示词当正文写进报告。另外「只渲染 prompt 没调模型」的返回值带 `isExist` 键，用它挡掉。

**另一个坑**：本工程同时存在 fastjson 与 fastjson2，**agent 模块用的是 fastjson v1**
（`com.alibaba.fastjson.JSONObject`）—— `AgentRuleExecuteReq#setRequestParams` 只收 v1 类型，导错包直接编译不过。

### 8.6 日志与容错（用户明确要求）

- **每次调用都记日志**：
  - 成功 → `【报告内容加工】知识库/智策引擎调用完成 reportNo= block=(块名) agentCode= 担保人= 字数= 耗时=ms`
  - 规则未命中 → `【报告内容加工】规则未命中 ruleCode= reportNo= guarantor= 耗时=ms`（**正常业务态，不是错误**）
  - 失败 → `【报告内容加工】失败(跳过该块) reportNo= block=(块名) agentCode= 入参= 异常堆栈`
  - 总结 → `【报告内容加工】风险要点总结完成 reportNo= 素材条数= 模型= 字数= 耗时=ms`
- **绝不影响整体流程**：`AgentReportContentProvider.provide()` 外层 `catch (Throwable)` 兜底只记日志 + 返回 null；
  块级异常由 `doProcess` 的分块隔离收进 `blockFailures` → `fail_reason` 软备注，报告**仍走 888 终态**。
  任何单块失败都不会中断整份报告，也不会让报告卡在 000。

### 8.7 AI 风险 = **命中的**经验规则；一行装两个同源产物（2026-09-17 第三轮）

用户口径：

> 「智策的校验结果我也是要的，跟补充分析是一起关联的，用报告详情页展示的命中的规则（ai风险），
> 明白？没有命中的其实就不用展示了」

#### 语义

**一条经验规则命中 = 一条 AI 风险行**，且这条规则同时产出两样东西，全部落在同一行：

| 落库列 | 内容 | 来源 | 是否可编辑 |
|---|---|---|---|
| `risk_desc` | **补充分析**（大模型出的风险文案） | `getPromptContent` 返回的 `answer` | 可（正文侧改正文会同步本列） |
| `check_result`（**新增列**） | **校验结果**（命中判定 + 事实表达式 + 校验溯源明细） | `executeRule` 的返回 | 否（只读留痕） |

两者是**同一次规则调用**的两个产物 ⇒ 天然一一关联，不需要额外关联表。

#### 「命中」的判定依据

**块内容非空**。未命中时 provider 返回 null → 实例 content 为空。
一处判定，三处复用（正文 `HIDE`、风险行生成、风险要点总结素材），不会互相错位。

#### `check_result` 装什么（**2026-09-17 用户二次澄清后收敛**）

原话：「我其实只要要个**是否命中**的结果，再加一个补充分析落表即可，
**溯源啥的目前没这个诉求**，溯源块是属于单独的内容块设计。」

⇒ 本列只是**一个结论字符串**（`VARCHAR(16)`）：`命中` / `未命中`。

| 列 | 内容 | 可编辑 |
|---|---|---|
| `risk_desc` | 补充分析（大模型风险文案） | ✅ 改正文时同步 |
| `check_result` | 校验结论（是否命中） | ❌ 只读留痕 |

⚠️ 本表**只落命中的规则**（未命中/校验失败的内容为空 ⇒ 不生成风险行），
所以落库值**恒为「命中」**。留这一列是为了语义自解释 + 将来若要落未命中记录时不用改表。

⛔ **不要往这里塞校验溯源明细**（事实表达式 / 涉及指标 / 命中值 / 取数完整性）——
用户明确说没这个诉求，而且**溯源是单独的内容块设计**（{@code fillType=SOURCE_LINK}，见 §9），
两者职责不同，不要混。

**仍然保留的一条后端日志口径**（不影响落库）：

> **「校验失败」≠「未命中」** —— 表达式无法执行时 `resultStatus=null`，若混为一谈就是把
> "这次校验根本没成立"伪装成业务结论（智策引擎前端 2026-09-16 已专门修过）。
> 后端单列一类日志 `【报告内容加工】规则校验失败(表达式未执行) ruleCode= …` 便于排查。

#### 担保人口径

标了 `guarantorName` 的块按企业担保人轮循，文案按段落拼接。
**校验结论不展开** —— "这次判定命中了"与是哪个担保人无关，一行一条结论即可。

## 九、溯源的两类设计（2026-09-17 第四轮：**已落地**）

### 9.1 定案口径

| 类别 | D 列 | fillType | analysisType | agentCode | content |
|---|---|---|---|---|---|
| **表格溯源** | 表格溯源 | **TABLE** | **TRACE_TABLE** | **表英文名**（`app_customer_info`） | 查表 → 拼 md 表格 |
| **链接溯源** | 链接溯源 | TEXT | **TRACE_LINK** | — | "链接开头"（信贷配置表未接入，本版留空） |

**为什么不统一用 `SOURCE_LINK`**（早先的提案）：前端 `blockToHtml` 把 `SOURCE_LINK` 渲染成
`<a href="${content}">` 外链按钮，而表格溯源的 content 是 md 表格文本 → 会渲染成 `<a href="| 表名 |…">`，
**直接坏掉**。把"溯源"放进 `analysisType` 这一维，`fillType` 只负责"怎么渲染"，两个维度正交（见 §10）。

### 9.2 表格溯源怎么取（`TraceTableBuilder`，已实现）

| 步骤 | 做法 |
|---|---|
| 表名 | 白名单 `^app_[a-z0-9_]+$` 后才拼 SQL（防注入） |
| 表头 | 从 `pg_catalog`（`pg_class`/`pg_attribute`/`pg_description`）取列中文注释，**带缓存**；先按 `current_schema()` 找、找不到再放宽全库 |
| 表头截断 | 注释在**第一个「（」处截断**（`控股类型（码值：…）` → `控股类型`）；无注释退回列名 |
| 列 | **全列输出、不过滤**（用户 2026-09-17 明确：`id`、`入库时间` 这些技术列**保留**） |
| 条件 | `reportNo→reportno`、`entName→customername`、`guarantorName→guarantorname`（与指标 SQL 同口径）；G 列的 `列=值` 令牌作为额外 where；**值走命名参数绑定**，不拼字符串 |
| 🔴 兜底 | 表里**没有那个列** → 跳过该条件 + 记日志（绝不当成"过滤生效了"）；无数据 / 表不存在 / 异常 → **return null**（块空 → HIDE，不报错、不中断整份报告） |
| 输出 | md 表格；单元格里的 `|` 转义、换行压平；上限 500 行 |

日志：`【报告内容加工】表格溯源完成 / 无内容 / 失败(跳过该块)`。

**前端契约**：`analysisType = TRACE_TABLE` 的块渲染成**可点入口**，点击弹大窗用 md 表格展示
（**不是**平铺在正文里）；`TRACE_LINK` 同理 —— 点击 → 调后端接口（拼参数 + SM4 加密）→ 跳信贷。

### 9.3 🔴 溯源块的「尾块归位」（用户 2026-09-17 准）

口径：**溯源行按该行的「最小章节」定位，并排在这个最小章节之后**。

但前端 `flattenCatalogs` 渲染目录树是「先渲染本节点的块、再渲染子节点」——
留在**章节级**（L1）的溯源块会出现在**章节标题之下、各小节之前**，不是"章末"。
`sortNo` 只能保证「同一 catalog 内」的排序，**跨不了节点**。

⇒ 生成器做 **尾块归位**：从「最小章节」往下取**最后一个后代目录**，把溯源块挂进去。
落在该分支最深处 → 渲染出来即"该最小章节之后"。
（另一条路是前端识别 `sortNo>=9000` 的"尾块"并延后渲染 —— 要改两个前端工程，未采用。）

配套两条硬约束（已进自校验脚本）：

- 溯源块的 `catalogCode` **不得指向有子目录的目录**；
- 溯源块 `sortNo` **必须 ≥ 9000**（独立序号段，保证在该目录内排在正文块之后）。

实测：37 个溯源块中 **15 个被下移**；二、三章本身无子目录（L1 即叶子）故保持挂 L1。

### 9.4 外部灌入（`EXTERNAL`）

`Risk-RiskReferenceAfter-Analysis-Customer-Suz`、`post_loan_industry_change_impact_code`
两个编号**暂未接入**，后续由别的接口直接落 `content`（TEXT/TABLE 都可能有）
⇒ `fillType=TEXT`、`analysisType=EXTERNAL`、`emptyStrategy=PLACEHOLDER`。
provider **显式跳过**它们 —— 否则会拿这两个编号当知识库配置编号去查，查不到就每次都往
`fail_reason` 里写一条"调用失败"。

### 9.5 关于 `app_guarantor_credit_info` 的条件

该表**没有 `subjectType` 列**（表内本身只有担保人数据），源表 G 列却写了 `限制subjectType=担保人`。
用户 2026-09-17 明确：**这个条件不要了**。生成器里有 `DROP_CONDITION_TABLES` 兜住这一类。
（`app_credit_report_info` 上的 `subjectType=借款人/担保人` **保留** —— 这张表同时存两类数据，
六章与十二章各引一次，不滤会查到混合数据。）

## 十、`fillType` × `analysisType` 两个维度是正交的（2026-09-17 用户定调）

用户原话：「`analysisType` 有值的情况，`fillType` 确实不需要拘泥于是表格还是文本是不是？」
—— **正确**，而且有硬证据：

- 前端 `blockToHtml` 只对 `TITLE` / `SOURCE_LINK` 分支；**TEXT 与 TABLE 走同一条路径**
  （都是 `${content}` 原始注入）。
- ⇒ **TABLE 今天不产生任何渲染差异**，它纯粹是个"声明"。

两个维度各回答一个问题：

| 维度 | 回答的问题 | 取值 |
|---|---|---|
| `fillType` | **怎么渲染** | `TITLE` / `TEXT` / `TABLE` / `SOURCE_LINK` |
| `analysisType` | **内容从哪来、怎么加工** | `ANALYSIS` / `RULE` / `TRACE_TABLE` / `TRACE_LINK` / `EXTERNAL` |

真正的"内容种类"由两维组合决定（行型矩阵）：

| 行型 | fillType | analysisType | 加工方式 | emptyStrategy |
|---|---|---|---|---|
| 报告头 | TITLE / TEXT | — | 固定文案（entName / "日常贷后检查报告" / 空） | PLACEHOLDER / HIDE |
| 知识库（正文） | TEXT | `ANALYSIS` | `getPromptContent(moduleCode=<知识库编号>)` | PLACEHOLDER |
| 经验库（规则） | TEXT | `RULE` | `executeRule` 判定 → 命中才取"补充分析" | **HIDE** |
| 风险要点总结 | TEXT | `ANALYSIS` | 汇总全部命中的 RULE 块 → 1 次大模型归纳 | **HIDE** |
| 风险要点条目 | TEXT | `ANALYSIS` | 复用对应 RULE 块内容（不额外调模型）+ 跳转锚点 | **HIDE** |
| 表格溯源 | **TABLE** | `TRACE_TABLE` | 查表 → 拼 md 表格 | **HIDE** |
| 链接溯源 | TEXT | `TRACE_LINK` | 拼"链接开头"（配置表未接入） | **HIDE** |
| 外部灌入 | TEXT | `EXTERNAL` | 别的接口直接落 content | PLACEHOLDER |

**为什么不把 TABLE 降级成 TEXT**：保留成本是 0、收益是信息 ——
将来做表头冻结 / 导出 Excel / 列宽时，这是唯一的线索。
所以最终口径是：**TABLE 留作声明，既不作为校验约束，也不作为渲染分支**。

**由此得到一条代码约定**（已落地，⛔ 别再收紧）：判"这个块要不要调 agent / 是不是规则块"
一律**只看 `analysisType`**：

- `validateTemplate`：`analysisType` 非空 ⇒ `fillType ∈ {TEXT, TABLE}`（这条放宽过两次，原因见 §8.3b 规则 4）；
- `isRuleBlock`：`(TEXT||TABLE) && RULE` —— 必须与 provider 的 `analysable`
  （`TEXT||TABLE`）同口径，否则将来某个规则块被标成 TABLE 时，
  会出现「正文有内容、AI 风险列表却少一条」。

## 十一、模拟数据（mock）提供者：与 blockCode 解耦（2026-09-18 重构）

> 开关**仍是** `report.mock-content.enabled`（用户 2026-09-18 决定保持 yml、不做运行时切换）
> ⇒ **改完必须重启**（`@ConditionalOnProperty` 是 bean 装配期判定）。

### 11.1 为什么必须改：旧 mock 与新模板「交集为 0」

`MockReportContentProvider` 原实现按 **blockCode** 查 `classpath:report-demo/demo-content.json`。
而模板重建后 blockCode 生成规则变过：

| | 形如 | 例 |
|---|---|---|
| 旧（JSON 里的） | 章缩写 + 序号 | `BLK_SUM_02` |
| 新（模板里的） | `V2_` + 章节全称缩写 + 类型字母 + 序号 | `V2_BLK_SUMMARY_A01` |

**实测对比**：JSON **82** 块 vs 模板 **182** 块 → **交集 0**（连报告头都对不上）。
⇒ 切回 mock 会得到一份**几乎全空**的报告。

### 11.2 新做法：按块类型造内容

`provide()` 不再看 blockCode，三级分流「报告头特判 → 可选 JSON 覆盖 → 按类型造」：

| 条件 | mock 产出 | 结果 |
|---|---|---|
| `catalogCode` 空 + 块名含「主标题」 | 客户名 | 正常 |
| `catalogCode` 空 + 块名含「副标题」 | 「日常贷后检查报告」 | 正常 |
| `catalogCode` 空 + 其它（说明块） | `null` | HIDE |
| `analysisType=RULE` | 「经校验，X 在「章节」命中规则：Y」+ `checkResult=命中` | 正常 |
| `analysisType=ANALYSIS` | 假分析文案 | 正常 |
| `analysisType=TRACE_TABLE` / `fillType=TABLE` | 3 行 md 表格 | 正常 |
| `analysisType=TRACE_LINK` | `null`（链接开头来自信贷，模拟态同样留空） | HIDE |
| `analysisType=EXTERNAL` | 占位文案 | 正常 |
| 其它 TEXT | 通用假文案 | 正常 |

**总结块**（阶段 2 回调 `provideRuleSummary`）：不调大模型，直接把命中的规则**按章节罗列**
（素材本来就是「已命中的 RULE 块」，这样条目块与它口径一致，也不会让 mock 变成"半真半假"）。

### 11.3 两个刻意的设计

**① 内容一律带 `【模拟数据】` 标识**（常量 `MockReportContentProvider.TAG`）。
报告是给人看的，真假必须一眼可分 —— 要纯演示效果就去掉这一个常量。

**② JSON 保留为「可选覆盖」**：按**当前** blockCode 往 `demo-content.json` 加条目即可覆盖该块
（便于对个别块定制假文案）。默认一条都命中不了，全部走类型造内容。
⚠️ 该 provider **不读任何数据库表**，只依赖 classpath 资源 —— 这点别搞混。

### 11.4 验证（真跑，不只看编译过）

临时类把 7 类输入各跑一遍，全部符合预期：

```
① 报告头：主标题=客户名 / 副标题=日常贷后检查报告 / 说明=null
② RULE  ：<p>【模拟数据】经校验，…在「六、征信情况和潜在风险」命中规则：…  [checkResult=命中]
③ ANALYSIS：<p>【模拟数据】针对…的「客户股东情况」：…
④ TRACE_TABLE：| 序号 | 项目 | 数值 | 单位 | 备注 | …（3 行 md）
⑤ TRACE_LINK：null
⑥ EXTERNAL：<p>【模拟数据】…该块内容由外部接口灌入…
⑦ 总结块：2 条素材 → <ol> 按章节罗列；0 条素材 → null
```

### 11.5 仍未解耦的一处（知道就行）

mock 内容能否落进报告，仍取决于**模板表里有没有这个块**（`isEnabled=1`）——
这是生成器「按模板逐块加工」的必然结果，不是 mock 的问题。
所以：**切 mock 不需要动模板**，但"模板里根本没有的块"mock 也变不出来。
